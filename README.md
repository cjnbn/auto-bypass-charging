# 自动旁路供电（KernelSU 模块）

> 让手机插着充电器时**由充电器直接给系统供电，电池既不充也不放**（下称「真旁路」）。
> 目的是减少边充边玩时的电池发热与损耗。

**这是一个针对特定机型做的模块**，原理与节点名都来自 MTK 平台，换机型大概率要重新摸节点。
开发与验证全程在一台 **Redmi Note 11T Pro（xaga）** 上完成，细节见 [`docs/`](docs/)。

---

## 一、怎么判断"成了"

只有一个判据：

| 现象 | 含义 |
|---|---|
| `battery/current_now == 0` **且** `usb/online == 1` | ✅ **真旁路**：适配器供电，电池不动 |
| `battery/current_now` 变成**正数** | ❌ 只是「停充」：充电停了，但手机改由电池供电（电量会掉） |
| `battery/current_now` 是**负数** | ❌ 还在充电 |

> 内核的符号约定是**充电为负、放电为正**，WebUI 里按用户习惯做了取反（充电显示 `+`）。
> ⚠️ 另外：写入控制节点后**要约 10 秒**主电源路径才接管系统负载，这期间 `current_now` 会短暂为正。
> **判断是否真旁路至少要看 15~20 秒**，只看前几秒很容易误判成"停充"。

## 二、安装

1. 需要 **KernelSU**（本项目在 v3.3.0 LKM 模式验证）或 Magisk，且已获取 root。
2. 从 [Releases](../../releases) 下载 zip，在 KernelSU 管理器里「安装模块」→ 重启。
3. **不需要元模块（metamodule）**：模块没有 `system/` 目录，做的事是往 procfs/sysfs 写运行时参数，
   没有东西需要挂载。

开机后守护进程由 `service.sh` 拉起；配置与日志放在 `/data/adb/bypass_charger/`（模块目录之外，更新模块不会丢）。

---

## 三、配置

配置文件：`/data/adb/bypass_charger/config.sh`（也可以直接在 WebUI 里改）

| 键 | 默认 | 含义 | 有效范围 |
|---|---|---|---|
| `ENABLE_THRESHOLD` | 95 | 充到多少开始旁路 | 用**原装 PD 快充头**时**实际下限是 80%**（见下）；用 5V 慢充/电脑 USB 口时任意值都行 |
| `DISABLE_THRESHOLD` | 80 | 掉到多少恢复充电 | 无限制（必须小于上面那个） |
| `CHECK_INTERVAL` | 60 | 轮询间隔（秒） | 最小 5 |
| `DEBUG` | 0 | 1 = 每轮打一条 `tick` 详细日志 | 排查问题时可临时打开 |

**为什么原装快充头下 80% 是下限**：这块 MTK 平台在低电量用**双充电泵（PPS 快充）**直灌电池，
而模块能压住泵的手段（`night_charging`）是走 MIUI 框架的、**框架只在电量 ≥80% 时才理会**。
所以设 80% 以下做不到 —— 它会一路充到 80% 才停。详见 [`docs/技术文档.md`](docs/技术文档.md) 第 2.4 节。

> 阈值是"**到点才开始旁路**"，不会把已经高于阈值的电量放下来（插上时 92%、阈值 85%，就直接在 92% 进旁路）。

## 四、WebUI

在 KernelSU 管理器里打开模块即可，**不需要 npm、不打包**，直接用 KernelSU 注入的 `window.ksu`。

- **状态**：徽章（旁路已开启 / 旁路无效 / 正常充电 / 未接充电器）、电池电流与功率、适配器、守护进程、**模式**
- **配置**：上面那四个键，保存后自动重启守护进程
- **手动操作**：
  - **自动** —— 按配置阈值自动进/出旁路（默认）
  - **开启旁路** —— **无视阈值**，只要插着充电器就一直保持旁路（拔掉充电器或切回「自动」才退出）
- **日志**：最近 30 条

## 五、命令行

```bash
CTL=/data/adb/modules/bypass_charger/bypassctl.sh

su -c "sh $CTL status"        # 结构化状态（KEY=VALUE，WebUI 读的就是它）
su -c "sh $CTL text"          # 给人看的
su -c "sh $CTL on"            # 一次性：立即进入旁路（不改模式）
su -c "sh $CTL off"           # 一次性：立即恢复充电
su -c "sh $CTL mode on"       # 切模式：手动旁路（无视阈值）
su -c "sh $CTL mode auto"     # 切模式：自动
su -c "sh $CTL restart"       # 重启守护进程
su -c "sh $CTL log 30"        # 看日志
```

## 六、工作原理（简版）

进旁路时**三个节点一起写**（并联冗余，"谁能生效谁顶上"）：

| 节点 | 写入 | 作用 |
|---|---|---|
| `/proc/mtk_battery_cmd/current_cmd` | `0 1` | 主力：泵闲着时（<80% 走 5V 直充、泵停了以后）由它把电池电流清零。同时是**状态判据** |
| `/sys/class/power_supply/battery/night_charging` | `1` | **压泵**：电量 ≥80% 时让 MIUI 框架立刻停充，充电泵没有负载就自己停了 |
| `/proc/mtk_battery_cmd/en_power_path` | `1` | 使能主电源路径，把「停充」升级成「真旁路」（适配器接管系统供电） |

退出时**先**写 `night_charging=0`（释放框架的 80% 保持），**再**写 `current_cmd="0 0"`。
顺序反了的话，充电会被框架卡在 80% 不再往上充。

**状态机**：

```
充电器在线 且 电量 >= ENABLE_THRESHOLD   -> 进入旁路
充电器在线 且 电量 <= DISABLE_THRESHOLD  -> 退出旁路
充电器被拔掉                             -> 立刻退出旁路（≤5 秒）
没有充电器时                             -> 不会进入旁路
```

守护进程每轮还会做三种**自愈**（任一成立就重打进入序列）：
① 说在旁路、但电池还在充（泵又抢回去了）；
② 压泵节点被外力改回 0；
③ 只做到「停充」——电池在给系统供电、而 `en_power_path` 没使能。

完整流程（含每个判定步骤、写入的成败判定、模式分叉）见
[`docs/模块运行流程图.md`](docs/模块运行流程图.md)。

## 七、已知限制

1. **原装 PD 快充头下，低电量时压不住充电泵** —— 旁路实际要等到 ≥80%（原因见第三节）。
   想在任何电量都能旁路，用 **5V 慢充 / 电脑 USB 口**（不走泵）。
2. **只在 Redmi Note 11T Pro / MIUI 13 / Android 12 / kernel 5.10.66 上验证过**。
   其他 MTK 机型节点名可能不同，需要自己对照 `nodes.conf` 摸一遍。
3. **`night_charging` 走 MIUI 框架**，所以它的行为受框架调度影响：
   我们验证时全程在夜间时段，**白天是否同样生效尚未实测**；过夜时 MIUI 会不会自己把电量补到 100% 也没验。
4. **日志只保留最近 30 条**（`LOG_KEEP_LINES`），更早的事件会被截掉 —— 要留证据请当场导出。
5. 直接关充电泵的三个节点（`cp_master/online`、`cp_slave/online`、`pd_cp_manager/request_ibus`）
   以及泵自己的限流口（`mtk-mst-div-chg` / `mtk-slv-div-chg` 的 `input_current_limit` 等）
   都被驱动挡住，写不进去 —— 这是"80% 下限"至今无法从根上解决的原因。

## 八、常见问题

**Q：为什么我把阈值设成 95，它却在 87% 就停了？**
A：旁路是"到点才进"，但**一旦进入就一直保持**（滞回）。87% 停下说明之前已经满足过进入条件；
想让它充到 95 再停，先确认进入阈值确实是 95、并且中途没有拔插过充电器。

**Q：为什么徽章显示「旁路无效」？**
A：状态节点写进去了，但电池还在充（`current_now` 是负数）—— 典型就是撞上了泵窗口。
模块会每 90 秒重打一次，等泵自己停下来就接管。

**Q：日志怎么这么少？**
A：正式版 `DEBUG=0`，只记状态机决策（进/出旁路、自愈、拔插、报错），且**只保留 30 条**。
要看每轮细节就把 `DEBUG` 设成 1——但那样 30 条只够 30 分钟。

**Q：卸载会不会留下"充不进电"的状态？**
A：`uninstall.sh` 会先杀守护进程，**先解锁**再逐个还原节点（`current_cmd`、`night_charging` 等），
并把权限还原成 644，每一步都写进 `run.log`（`uninstall:` 前缀）。

## 九、仓库结构

```
module/                     模块源码（带注释，改东西改这里）
  module.prop               模块元信息
  nodes.conf                ★ 控制策略唯一来源（节点、写入值、备用方案）
  auto_bypass.sh            ★ 守护进程（状态机、自愈、日志）
  bypassctl.sh              ★ 控制工具（status/text/on/off/mode/restart/log）
  service.sh / customize.sh / uninstall.sh
  webroot/index.html        ★ WebUI
  META-INF/                 标准安装器（KernelSU 不读，仅供 Magisk 兼容）
docs/
  技术文档.md               完整原理、节点普查、调试工作流、脚本性能约定
  实测记录.md               ★ 全部原始实测数据（含失败的结论与踩过的坑）
  模块运行流程图.md          运行判定流程图（Mermaid + 纯文本两版）
tests/                      做上面那些实测时用的脚本（一次性实验用，不参与模块运行）
```

**发布包**：源码改动后按 `module.prop` 的版本号打 zip，作为 **Release 附件**发布
（`release/` 里的 zip 不进仓库树，见 `.gitignore`）。
