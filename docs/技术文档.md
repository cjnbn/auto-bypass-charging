## 一、这个模块要做什么

让手机插着充电器时**由充电器直接供电，电池既不充也不放**（下称「真旁路」或「电池闲置」）。
目的：减少边充边玩时的电池发热和损耗。

**判断是否真的做到了，只有一个判据：**

| 现象 | 含义 |
|---|---|
| `battery/current_now == 0` **且** `usb/online == 1` | ✅ 真旁路：适配器供电，电池不动 |
| `battery/current_now` 变成**正数** | ❌ 只是「停充」：充电停了，但手机转由电池供电 |
| `battery/current_now` 是**负数** | ❌ 还在充电 |

> 注意 `battery/current_now` 的内核符号约定是**充电为负、放电为正**，
> 与 WebUI 里的显示相反（WebUI 按用户习惯做了取反，见第五节）。

## 二、核心技术结论

### 2.1 难点：快充走的是充电泵，绕开了主充电器

这是整个项目最关键的一条。

| 供电方式 | 电流路径 | 单独写 `current_cmd="0 1"` | 实测 |
|---|---|---|---|
| 电脑 USB 口（5V，`real_type=Unknown`） | 主开关充电器 | **有效** | `ibat=0` 持续 90 秒 ✅ |
| 原装充电头（PD 快充，`real_type=USB_PD`）**且充电泵全速** | **充电泵** `cp_master/cp_slave` | **无效** | `cmd=[0 1]` 下仍以 **1.5A** 充电，`cp_ibus` 从 3 飙到 579 ❌ |
| 原装充电头**但充电泵已停**（约 89%+，电流降到 1.5A 左右） | 主开关充电器 | **有效** | `cmd=[0 1]` → `ibat=0` 稳住 ✅（见 2.4） |

原始现象由采样日志抓到（`cmd` 全程没被重置）：

```
14:03:56  ibat=+522000  usb_on=0  type=Unknown  cp_ibus=3    cmd=[0 1]   ← 电脑口拔线
14:04:01  ibat=+677000  usb_on=1  type=USB_PD   cp_ibus=3    cmd=[0 1]   ← 充电头插入
14:04:06  ibat=-122000  usb_on=1  type=USB_PD   cp_ibus=267  cmd=[0 1]   ← 充电泵启动，开始充
14:05:41  ibat=-1503000 usb_on=1  type=USB_PD   cp_ibus=579  cmd=[0 1]   ← 1.5A 灌进电池
```

### 2.2 解法：`current_cmd` 是主力，v11.14 起再加两个节点压泵

**先澄清一个曾经的错误结论。** 本项目长期认为必须用一套「两段式」
（`sc_tuisoc` → `enable_sc` 0→1 → `current_cmd`），理由是「先用 MTK 智能充电
打断 PD 快充，退回主充电路径」。**这是错的** —— 详见 `实测记录.md` 第十二节。

决定性实验（把 `enable_sc` 和 `sc_tuisoc` 都设成远离模块配置的值，
即 MIUI 智能充电完全不参与）：

```
基线（已确认全速充电）  ibat = -1439000
只写 current_cmd=0 1 → ibat = 0           持续 60 秒
只写 current_cmd=0 0 → ibat = -1359000    立刻恢复全速充电
```

**`current_cmd` 单独就能停充和恢复**，所以 v11.11～v11.13 的策略只有它一条。它的好处是
实打实的：1 个写入、1 秒完成，可回读，不跟 MIUI 抢 `enable_sc`（内核日志显示框架
**每 10 秒**就写一次 `enable smartcharging: 1`）。

> 那两条 `enable_sc`/`sc_tuisoc` 也**不解决充电泵问题**：泵全速时重打三次
> 依然完全无效（内核回 `ans:ignore`）。它们唯一「看起来有用」的那次验证
> （`实测记录.md` 第三节）其实是在泵闲着的时候做的，功劳被误记了。

**但它有一个死穴：充电泵全速时（约 80~88%）完全无效** —— 就是 §2.4 那个洞。
2026-10-06 晚找到了绕开的办法，所以 **v11.14 起进入旁路时写三个节点**：

```sh
echo "0 1" > /proc/mtk_battery_cmd/current_cmd                # 主力：泵闲着时由它干活
echo 1     > /sys/class/power_supply/battery/night_charging   # ★ 压在充电泵（≥80% 才生效）
echo 1     > /proc/mtk_battery_cmd/en_power_path              # 把「停充」升级成「真旁路」
# 退出时【先】写 night_charging=0（否则框架把充电永久卡在 80%），再写 current_cmd="0 0"
```

实测（真机，87~86% 泵全速）：`off` 立刻恢复 −1.45A 充电；`on` 立刻 `ibat=0` 并稳定保持。
原理与全部原始数据见 §2.4 ★★ 和 `实测记录.md` 第十五节。

### 2.3 一个必须知道的教训：观察窗口不能太短

本项目最初测 `enable_sc` 时只等了 **10 秒**就判定它「无效」，
把当时唯一看着有效的机制否掉了，多绕了一整轮。**观察窗口一定不能短于 45 秒。**

（虽然那个机制本身后来被证明是多余的，但「过早下结论」这个教训仍然成立。
同类的错误还犯过一次，见 `实测记录.md` 第十一节那个 `constant_charge_current`。）

### 2.4 ⚠️ `current_cmd` 改不掉的限制：充电泵（**但 2026-10-06 找到了绕开的办法，见下方 ★★**）

**这是本节最重要的内容。** 原装充电头 PD 快充时，电流经充电泵
`cp_master`/`cp_slave` 直灌电池、绕开主开关充电器，而 `current_cmd` 只管主充电器：

| 充电泵状态 | `cp_ibus` | 典型 `ibat` | 内核回答 | `current_cmd` 旁路能否生效 |
|---|---|---|---|---|
| 全速（PPS 快充） | 500～1448 | -1.5 ～ **-5.5 A** | `ans:ignore` | ❌ **不能** |
| 闲置（主充电器路径） | 1～3 | -1.5 A 或 0 | — | ✅ **能** |

> 补测：低电量（65%）时泵比 89% 时凶得多，`ibat` 可到 **-5.5A**、`cp_ibus` 到 **1448**。

**实际后果：旁路生效点比设定阈值高。** 实测（阈值设 80%）：

```
80 ~ 88%   充电泵全速运行  → 旁路无效，继续充
约 89%+    充电泵停止      → current_cmd 立刻接管，电池闲置并稳住
```

所以最终稳定点是 **约 90% 而不是配置的 80%**。这不是代码 bug、也不是阈值没生效，
是驱动层限制 —— **别去改阈值逻辑，改了也没用**。

能直接关泵的三个节点都试过，走不通：

```
/sys/class/power_supply/cp_master/online
/sys/class/power_supply/cp_slave/online
/sys/devices/platform/pd_cp_manager/request_ibus
→ -w 显示可写，实际 Permission denied
```

#### ★★ 泵是可以压下去的：`night_charging` + `en_power_path`（2026-10-06 晚实测）

**这条推翻了"泵挡路改不掉"的旧结论。** 原始数据见 `实测记录.md` **第十五节**，要点：

| 测试（都在泵全速、`ibat` 约 −2.1~−5.3A 下） | 结果 |
|---|---|
| `current_cmd="0 1"` | ❌ 完全无效（电流纹丝不动） |
| `current_cmd="0 1"` **+** `en_power_path=1` | ❌ 仍无效 |
| `en_power_path=1` 单独 | ❌ 杀不掉泵 |
| **`night_charging=1`** | ✅ **泵立刻停摆**（`cp` 585→3），但结果是**停充**（`en_pp=0` 时 `ibat` 转正） |
| **`night_charging=1` + `en_power_path=1`** | ✅★ **完整真旁路**：`ibat=0` 持续 3 分钟、适配器供电、电量不涨 |

**机理**：`night_charging` 走的是 MIUI 智能充电/夜间充电那套逻辑，**以 80% 为界** ——
电量 **≥80%** 写它就立刻停充（泵没有负载，自己就停了）；**<80% 则完全不理会**。
而 `en_power_path` 决定"停充"之后**谁给系统供电**：`0`（泵充电时驱动默认就是这个值）→ 电池供电 = 停充；
`1` → 适配器供电 = **真旁路**。

**三种场景正好互补，所以进入旁路时三条一起写**：

```sh
printf '%s\n' '0 1' > /proc/mtk_battery_cmd/current_cmd                # <80% 与泵停了以后的主力
printf '%s\n' 1     > /sys/class/power_supply/battery/night_charging  # 80~88% 泵窗口由它压泵
printf '%s\n' 1     > /proc/mtk_battery_cmd/en_power_path             # 把"停充"变成"真旁路"
```

退出旁路时 **`night_charging` 必须先写回 0**，否则框架会一直把充电保持在 80% 不再往上充。
（`uninstall.sh` 的 `RESTORE_LIST` 里本来就有 `night_charging|0`，没问题。）

> **现状**：以上三条已经**写进模块**（v11.14 的 `BYPASS_ON_ACTIONS`），并在真机跑通 ——
> 87% 泵全速下 `on` 立刻 `ibat=0`、`off` 立刻恢复 −1.45A 充电。
> 仍未闭环的是**长期行为**（白天是否同样生效、过夜会不会被 MIUI 补到 100%），见第八节第 1、2 条。
>
> ⚠️ **这个副作用已在 v11.16 修掉**：拔掉充电器时模块会**自动退出旁路**（≤5 秒内察觉），
> 而且**没有充电器时不会进入旁路** —— 所以重新插上会按你的阈值从头走一遍。
> 细节见 §2.5。

> **v11.15 又多了一层保险**：`night_charging` 的属主是 `system:system`（正是 MIUI 充电服务的身份），
> 我们实测遇到过**一次**"写入 1 之后自己变回 0"。所以加了 `chmod 440` 上锁 + 守护进程每轮自愈。
>
> ⚠️⚠️ **v11.16 修正了一个我自己写出来的 bug**：`chmod 440` 之后**连我们自己都写不进去** ——
> 实测 ksu 的 root 有 `CAP_FOWNER`（能 chmod），但**没有 `CAP_DAC_OVERRIDE`**，
> 往 440 的文件里写会直接 `Permission denied`，节点被**卡死在 1**（真实发生过，当时 `off` 命令失效）。
> 所以 `write_node()` 现在的顺序是：**先 `chmod 644` 解锁 → 写值 → 写 1 才 `chmod 440`**。
> **顺序绝不能反** —— 酷安帖子里"关的时候先 `chmod 660` 再写 0"就是这个原因。
>
> ⚠️ 如实说明：**"不加 chmod 就会被改回"这条我们没能复现**（不加 chmod 观察 5 分钟没问题，
> 上锁后 10 分钟也没问题），所以 chmod 属于"按作者原版的做法 + 机制上说得通"的保险，
> **真正兜底的是自愈**。原始数据见 `实测记录.md` 第 15.8 节。

#### 停充范围能设到多少？（直接决定你怎么配）

| 充电器 | 能否按你设的阈值停 |
|---|---|
| **原装 PD 快充头** | ✅ **80% 及以上都行** —— 实测 84%、86% 写 `night_charging=1` 都**立刻停**（泵当场死）；90 / 95 没有逐点实测，但框架的条件就是"≥80"，机制上同样成立<br>❌ **设到 80% 以下做不到** —— 低于 80% 时框架不理 `night_charging`，而 `current_cmd` 又被泵挡着，实际会一直充到 80% 才停（等于被兜到 80%） |
| **电脑 USB 口 / 5V 慢充**（不走泵） | ✅ **任意阈值都行** —— `current_cmd` 不受电量限制（72% 实测 15 秒就停，见 §2.2） |

`DISABLE_THRESHOLD`（掉到多少恢复充电）不受任何限制。
另外阈值是"**到点才开始旁路**"，不会把已经高于阈值的电量放下来。

#### 二类（停充）节点也能让泵停摆 —— 代价是转电池供电

泵全速时写 `battery/input_suspend=1` 或 `usb/input_suspend=1`，`cp_ibus` 也会在 **5 秒内
从 ~570 掉到 1~3**（低电量泵最凶时实测从 1376 掉到 3）。机理是它们切的是**电池输入路径** ——
泵没有可灌的负载。代价是手机转为电池供电（+43~+790 mA 放电），低电量时会持续掉电 ——
它只解决"不再往里灌电"，不解决发热。兜底方案见 `nodes.conf` 的方案 C1/C2。

### 2.5 插拔充电器后的行为（v11.16 起是一套完整的状态机）

```
充电器在线 且 电量 >= ENABLE_THRESHOLD   -> 进入旁路
充电器在线 且 电量 <= DISABLE_THRESHOLD  -> 退出旁路
充电器被拔掉                             -> 立刻退出旁路（≤5 秒，日志会写「充电器已拔…」）
没有充电器时                             -> 【不会】进入旁路
插上充电器 / 电量爬到阈值                 -> 进入旁路
```

- **为什么要"拔掉就退出"**：只要 `night_charging=1` 挂着，MIUI 就把充电上限压在 80%。
  不主动退出的话，"拔掉再插上、且电量低于 80%"时会先充到 80% 就停 —— 用户设的阈值
  （比如 90）在这条路径上失效。这也是 v11.16 之前的已知副作用。
- **为什么"没充电器不进旁路"**：没有充电器时进旁路毫无意义，而且会留下 `night_charging=1`
  —— 正是上面那个副作用的根源。所以进入条件里加了 `usb/online != 0`（读不到就按老行为放行）。
- **5 秒是 `nap_watch` 换来的**：主循环一轮默认 60 秒，若"拔掉再插上"整个落在同一轮里就检测不到。
  所以等待被拆成 5 秒一步，每步瞄一眼 `usb/online`，一旦掉线立刻返回。
  代价是旁路态下每分钟多约 11 次 fork（`sleep` 是 busybox 的 NOFORK applet，1ms 级），可忽略。
- **仍然存在的自愈**（与插拔无关的那部分）：每轮检查
  「状态节点说在旁路，但电池还在被充」→ 自动重打（防 PD 重新协商回泵快充）。
  **重打需要 60 秒轮询 + 90 秒冷却，最坏约 2.5 分钟**（本次启动后的首轮不受冷却限制）。
  手动执行 `bypassctl.sh on`（见 4.4）可以马上生效 —— v11.12 起 WebUI 上不再有这个按钮。

### 本模块【不需要】元模块（metamodule）

有一个容易搞混的点，在这里写清楚：

**不需要，而且也不依赖它。**

依据：

1. KernelSU 的[元模块文档](https://kernelsu.org/zh_CN/guide/metamodule.html)明确写着
   「模块中的 `system` 目录只有在用户安装了提供挂载功能的元模块时才会被挂载」，
   常见问题里也写着「**对于模块开发者**：不需要，您正常开发模块。
   仅当您的模块需要挂载时，用户才需要元模块」。
2. **本模块没有 `system/` 目录** —— 目录里只有脚本、`nodes.conf`、`module.prop`、`webroot/`，
   没有任何要覆盖到系统分区的东西。
3. `ksud module list` 里本模块的 **`"mount": "false"`** —— 这是 KernelSU 自己算出来的
   （判据是「有 `system` 目录且没有 `skip_mount`」）。
4. 本模块实际做的事情是**往 procfs / sysfs 写值**
   （`/proc/mtk_battery_cmd/*`、`/sys/devices/platform/charger/*`、`/sys/class/power_supply/*`），
   这些是**运行时内核接口**，不是系统分区上的文件，没有东西需要挂载。
5. 只用到生命周期脚本（`service.sh`）+ WebUI + 模块配置，
   文档里说明这几项「无需元模块即可工作」。

**实际意义**：用户卸载元模块（例如把 `mountify` 换成别的、或者干脆不装）**不会影响本模块**。
本项目实测的那台设备上装的是 `mountify`（`metamodule=true`），
`/data/adb/metamodule -> /data/adb/modules/mountify`，但那是给
`scene_swap_controller` 这类带 `system/` 的模块用的，跟本模块无关。

### ⚠️ 守护进程会被系统冻结（已修，但务必知道）

**这是本项目遇到的最阴的一个坑** —— 表现是「模块突然完全失效，日志一个字都不写」。

原因：从 KernelSU 管理器的 WebUI 里点「保存并重启守护进程」时，新守护进程会
**继承管理器 App 的 cgroup**（形如 `0::/uid_10228/...`）。用户一离开管理器，
Android 就把整个 cgroup 冻结，守护进程随之进入 `do_freezer_trap`：

```
wchan = do_freezer_trap
utime+stime 停在上次 tick 不再增长
日志不写、阈值不触发、什么都不做
```

而 `pgrep` 仍然能找到它，`ps` 也显示 `S`（睡眠），**看起来一切正常**。

| 启动方式 | 落到的 cgroup | 会被冻结吗 |
|---|---|---|
| **WebUI 点重启** | `0::/uid_10228/...`（管理器 App） | ❌ **会** |
| adb / 开机 `service.sh` | `0::/`（根 cgroup） | ✅ 不会 |

**修法**：`auto_bypass.sh` 和 `bypassctl.sh` 启动时都把自身移出应用 cgroup：

```sh
CGROUP_BEFORE=$(sed -n 's/^0:://p' /proc/$$/cgroup 2>/dev/null)
if [ "$CGROUP_BEFORE" != "/" ] && [ -w /sys/fs/cgroup/cgroup.procs ]; then
  echo $$ > /sys/fs/cgroup/cgroup.procs 2>/dev/null
fi
```

子进程会继承新 cgroup，所以只需在启动时做一次。
**改这两个脚本时千万不要删掉这段。** 启动日志里会留痕：

```
debug: cgroup=/uid_10228 -> /（非 / 会被系统冻结）
```

`bypassctl.sh` 也要做同样处理 —— 否则从 WebUI 调用它（保存配置后的 `restart`、每 3 秒一次的
`status`）时中途切走，动作序列会被冻结在半路：最坏情况是 `restart` 里刚杀完旧的守护进程就
被冻住，**模块直接停摆而界面上看不出原因**。v11.12 撤掉 WebUI 的手动开关按钮之后这条依然成立。

### 各文件要点

- **`nodes.conf`** —— 所有控制节点、写入值、说明都在这。**要改控制策略只改这个文件**，
  三个脚本都从这里读。文件里还带了几套注释掉的备用方案（方案 A/B/C）。
- **`auto_bypass.sh`** —— 守护进程。负责：读配置、按阈值触发进入/退出、状态自愈、
  DEBUG 详细日志。配置存在 `/data/adb/bypass_charger/config.sh`（**模块目录之外**，
  这样更新模块不会把用户配置冲掉）。
- **`bypassctl.sh`** —— WebUI 和命令行共用的控制入口。
  `status` 输出 `KEY=VALUE` 供 WebUI 解析；`text` 输出给人看的报告。
- **写入成败一律看"读回值"**（`write_node()`，`auto_bypass.sh` 和 `bypassctl.sh` 各有一份）——
  `battery/input_suspend` 这类 `power_supply` 节点的 store 函数会**先改状态、再返回 `-EINVAL`**：
  `write` 报 `Invalid argument`，但值和动作**已经生效**。所以用 `write` 的返回值判断成败
  会把成功的动作记成 `ACTION FAILED`。**别把它改回 `if echo > node`**
  （详见第八节第 8 条与 `实测记录.md` 第十四节）。
- **`webroot/index.html`** —— WebUI。**不依赖 npm/打包器**，
  直接调 KernelSU 注入的 `window.ksu` 原生对象（见第五节）。
  **状态展示以 WebUI 为准** —— 模块列表的「介绍」栏用的是 `module.prop` 里
  写死的静态文字，曾经做过动态状态显示，后来因为和 WebUI 功能重复而撤掉了，
  相关尝试记录在 `实测记录.md` 第七～九节（含一个值得看的缓存教训）。

### 性能 / 省电设计（改这两个脚本前先看这段）

这台机器上**每 fork+exec 一个 toybox 小程序要 10～20 ms**，比脚本逻辑本身贵得多。
实测（数据见 `实测记录.md` 第十节）：

| 写法 | 每次成本 |
|---|---|
| `$(cat f \| tr -cd '0-9')` | 32 ms |
| `$(cat f \| tr -s ' \t' ' ' \| sed …)` | 47 ms |
| `$(date +%s)` | 20 ms |
| `$(wc -c < f)` | 19 ms |
| **`read -r v < f`（shell 内建）** | **< 1 ms** |

所以两个脚本里**凡是读节点、读配置都走 `read` 内建**
（`read_val` / `read_digits_val` / `read_control_state` / `conf_val` / `module_version` /
`sc_orig_val`）。**加新代码时请沿用这个模式**，不要再写 `$(cat … | tr …)`。

**用 `read` 内建必须注意两个坑（都实测踩过）：**

1. **`read` 失败时不会清空变量。** 文件不存在或读不到时，变量会**保留上一次的值**，
   而 `read` 只是返回 1。所以必须**先置空**：
   ```sh
   READ_VAL=""
   read -r READ_VAL 2>/dev/null < "$1"
   ```
   少了第一行，就会拿上一次的旧值去比阈值 —— 这种 bug 极难发现。
2. **`read` 不折叠内部的连续空白。** `"0  1"` 读出来仍是 `"0  1"`，
   而老的 `cat | tr -s ' \t' ' ' | sed …` 会归一成 `"0 1"`。
   状态判定是拿字符串和 `STATE_STOP="0 1"` 比的，所以：
   - 常见路径用内建直比
   - **比不中时回退到老写法兜底**（见 `read_control_state` / `read_state_node`）
   - 但**节点读不到（空值）时不要回退**，否则节点一坏就每轮白起三个进程

另外几处**摊还**处理，改的时候别退回去：

- `log()` 的日志文件**只保留最近 30 条**（`LOG_KEEP_LINES`，v12.3 起）：写满之后每条会多做一次
  `tail -n 30` + `mv`（两个 fork，约 20~40ms），正式版一天几条、可忽略；
  `chmod 600` 只在文件新建/截尾后做一次 —— 原来每条日志都要 fork 一个 `chmod`
- 守护进程的「重打冷却」用**轮数**而不是墙上时间 —— 原来每轮都要 fork 一个 `date` 只为算冷却

**剩下的开销**（优化后仍占大头，属于固有成本，别去动）：
`log()` 里的 `date`（日志时间戳，DEBUG=1 时每轮一条）和 `nap()` 里的 `sleep`
（可中断等待，去掉就没法快速响应 SIGTERM）。想再降只能关 DEBUG 或调大
`CHECK_INTERVAL`，那两个都是功能/可观测性取舍，不是免费的。

### 状态目录（不在模块目录内）

```
/data/adb/bypass_charger/
├── config.sh         用户配置（ENABLE_THRESHOLD / DISABLE_THRESHOLD / CHECK_INTERVAL / DEBUG）
├── mode              运行模式（v12.1 新增）：auto = 按阈值自动；on = 手动强制旁路
├── run.log           运行日志（**只保留最近 30 条**，v12.3 起；旧行会被自动截掉）
├── run.log.old       【遗留】v12.2 及以前按 64KB 轮转留下的旧日志，新代码不会再生成它
│                     （里面是很久以前的历史，确认不需要就 `rm` 掉）
├── daemon.pid        守护进程 PID
└── sc_tuisoc.orig    【遗留，当前策略已不用】早期两段式方案记录的原值
```

> ⚠️ 因为日志**只留 30 条**，重要事件如果发生在很多条之前就会被截掉：
> 要长留证据就当时就复制出来，或者临时把 `DEBUG=1` 打开（每轮一条，30 条很快就翻过去，**不适合长期开**）。

## 四、调试工作流（重要）

### 4.1 热更新 —— 不用重装、不用重启

模块在 active 目录里，直接覆盖文件即可，**改完退出 WebUI 重进就能看到新界面**：

```bash
# 1. 推送新文件
adb push module/webroot/index.html /data/local/tmp/index.html

# 2. 覆盖进模块目录（注意权限和 SELinux context）
adb shell su -c "
  M=/data/adb/modules/bypass_charger
  cp -f /data/local/tmp/index.html \$M/webroot/index.html
  chmod 0644 \$M/webroot/index.html
  chcon u:object_r:system_file:s0 \$M/webroot/index.html
"

# 3. 如果改的是脚本，重启守护进程让它生效
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh restart"
```

**改 `.sh` 一律 chmod 0755，改 `index.html`/`nodes.conf` 一律 chmod 0644。**

推完**一定核对 md5**，别信 `adb push` 的"1 file pushed"：

```bash
adb shell su -c "md5sum /data/adb/modules/bypass_charger/webroot/index.html"
# 本地（Windows）：Get-FileHash -Algorithm MD5 module\webroot\index.html
```

### 4.2 推之前一定要做的校验

```bash
# 脚本语法（一定要做，nodes.conf 是被 source 的，语法错会让守护进程直接挂）
adb shell "sh -n /data/local/tmp/xxx.sh"

# WebUI 的 JS 语法
node --check <(抽出 index.html 里 <script> 的内容)
```

上面那条 `node --check` 的写法在 Windows 的 PowerShell 里跑不了（没有进程替换），实际做法是
用正则把 `<script>` 里的内容写成一个临时 `.js` 再 `node --check`：

```powershell
$html = Get-Content 'module\webroot\index.html' -Raw
$js   = [regex]::Match($html,'(?s)<script>(.*?)</script>').Groups[1].Value
[System.IO.File]::WriteAllText("$env:TEMP\ui_check.js", $js, [System.Text.UTF8Encoding]::new($false))
& $node --check "$env:TEMP\ui_check.js"          # 退出码 0 = 通过
```

顺手值得再查两条（都是这一版真踩过的）：文件**必须保持 LF 行尾**（用 Windows 编辑器改容易变 CRLF），
以及 `<div>` 开闭数量是否相等。

### 4.3 看日志

```bash
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh status"   # 结构化状态
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh text"     # 给人看的
adb shell su -c "tail -50 /data/adb/bypass_charger/run.log"                 # 日志
```

DEBUG=1 时每轮会打一条 `tick`：

```
tick cap=91 state=on ibat=0 usb_on=1 usb_in=710 node=[0 1] cp=1 type=USB_PD
                ↑        ↑        ↑     ↑          ↑      ↑     ↑
            缓存状态  电池电流  适配器在线 适配器电流 节点值 泵电流 接口类型
```

### 4.4 手动操作

```bash
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh on"    # 一次性：立即进入旁路
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh off"   # 一次性：立即恢复充电
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh mode on"    # 切模式：手动旁路（无视阈值）
adb shell su -c "sh /data/adb/modules/bypass_charger/bypassctl.sh mode auto"  # 切模式：自动（按阈值）
```

- `on` / `off` 是**一次性动作**，不改模式 —— 守护进程下一轮会按当前模式重新判定，可能把你刚做的动作改回去。
- `mode on` / `mode auto` 改的是**运行模式**（写在 `$STATE_DIR/mode`），改完会给守护进程发 `USR1`，
  **立刻重新判定**（不用等下一轮）。WebUI 的「手动操作」卡片点这两个按钮走的就是这条命令。

**v11.12 起 WebUI 上曾经没有手动按钮，v12.1 又把它们加回来了**（用户要求，做成了"模式"而不是"一次性动作"）。
`restart` / `log [n]` 没有单独的界面按钮（WebUI 内部就在调它们：刷新日志、重启守护进程）。

### 4.5 adb 连接的坑（Windows 环境特有）

- **adb 不在 PATH 里**，调用时要写全路径（把下面示例里的路径换成你自己的位置）
- **每次命令调用都会重启 adb server**，所以每条命令前都要重新 `adb connect`。
  看起来又长又重复，是这个原因。
- **`adb shell` 是普通用户身份，读不到 `/data/adb` 下的任何东西**（该目录 0700 root）。
  所有涉及模块目录、`config.sh`、`run.log` 的命令都必须套一层 `su -c`，
  否则会得到一句误导性的 `Permission denied` —— 别误判成"文件权限被改坏了"。
  WebUI 里没有这个问题：`ksu.exec` 本身就是 root。
  排查时可以用这条一次跑完：`adb shell "su -c '...'"`（注意 PowerShell 里用 here-string 传，
  内层引号才不会被打散）。
- 无线调试端口：本机曾用 `adb tcpip 5555`（传统方式，免配对），
  也会用系统自带的无线调试端口（**注意：重启 adbd 后系统端口会变**）。
- 手机 USB 插电脑时无法同时插充电头测试，**测快充必须走无线调试**。

## 五、WebUI 技术要点

KernelSU 向 WebView 注入原生对象 `window.ksu`，npm 包 `kernelsu` 只是它的薄封装。
本项目**不依赖 npm、不用打包器**，直接调原生 API：

```js
ksu.exec(command, JSON.stringify(options), callbackName)
// 执行完回调 window[callbackName](errno, stdout, stderr)
```

其余可用的：`ksu.spawn` / `ksu.toast` / `ksu.moduleInfo` / `ksu.fullScreen` / `ksu.exit`。
模块 id 通过 `ksu.moduleInfo()` 获取，据此拼出模块目录路径。

### 显示约定（已按用户要求调整过）

- **电池电流显示做取了反**：内核是「充电为负、放电为正」，
  WebUI 按用户习惯显示成**放电为 `-`、充电为 `+`**。
- **功率 W 的电压单位不同**：`battery/voltage_now` 是 **µV**，`usb/voltage_now` 是 **mV**。
  两个函数里的除数不一样，改的时候注意。
- **PD 快充时「适配器」电流节点读数是 0**（电走充电泵，不经过 `usb/input_current_now`），
  只有进了旁路退回 5V 主充电路径后读数才准。这不是 bug。
- 配置保存时会**只替换那 4 个键**，保留用户在 config.sh 里自己加的其它键；
  写文件用 base64 管道避免引号转义问题。

### 界面上撤过什么、又加回了什么（避免"补回来"和"又删掉"来回折腾）

| 版本 | 界面动作 | 说明 |
|---|---|---|
| v11.12 | **删掉**状态卡片的「电量」行（`#s-cap`） | 用户要求做减法。`status` 输出里**仍然保留 `CAPACITY=`**，只是界面不显示。**这条不要再补回来** |
| v11.12 | **删掉**「手动操作」卡片（4 个按钮） | 同上。连带清掉 `manual()` 与 `button.danger` |
