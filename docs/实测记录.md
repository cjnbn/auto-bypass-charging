## 一、节点能力总表

在 **Redmi Note 11T Pro / MIUI 13 / kernel 5.10.66** 上逐个实测的结论。

### 【一类】真旁路 —— 电池既不充也不放

| 节点 | 写入 | 生效条件 | 原始证据 |
|---|---|---|---|
| `/proc/mtk_battery_cmd/current_cmd` | `0 1` / `0 0` | 只在**非充电泵路径**（5V 直充）下有效 | 电脑口 `ibat=0` 持续 90 秒（见第四节） |
| `/sys/devices/platform/charger/enable_sc` | `1` / `0` | 能打断 PD 快充；约 15～30 秒收敛 | 充电头 `ibat=0`、`usb_on=1`、`cp_ibus=1`（见第三节） |
| `/sys/devices/platform/charger/sc_tuisoc` | `<目标电量>` / `<原值>` | 与 `enable_sc` 配套使用 | 同上 |

### 【二类】只能「停充」—— 停充后电池转为供电

判据：写完之后 `ibat` 变成**正数**（放电），而不是 0。

| 节点 | 写入 | 实测放电电流 | 备注 |
|---|---|---|---|
| `battery/input_suspend` | `1` | **+541 mA** | 电脑口和充电头都有效；`usb/online` 掉 0 |
| `usb/input_suspend` | `1` | **+522 mA** | 同上 |
| `battery/night_charging` | `1` | **+488 mA** | 充电头下有效（`cp_ibus=1`），但 `usb/online` 保持 1；**电脑口 70% 时完全无效** |
| `charger/input_current` | `100` | **+390 mA** | `-1` 表示不限制 |
| `/proc/mtk_battery_cmd/en_power_path` | `0` | **+141 mA** | 切断输入（`usb_in=0`）；写空串返回 `bad argument` |

> ⚠️ **本表有两条已被 2026-10-06 的复测推翻/修正**，另有一条新增重要结论
> （停充节点**不受充电泵限制**）。先看第十四节再引用本表：
> `charger/input_current` 实际上是**基本无效**（上表的 +390mA 是采到了写入瞬间
> 约 10~15 秒的过渡窗口）；`battery/night_charging` 复测到的行为是**真旁路**
> （`ibat=0` 且适配器继续供电），不是停充。

### 【三类】试过但无效

| 节点 | 结果 |
|---|---|
| `battery/charge_control_limit` | 写 1，无变化 |
| `battery/smart_batt` | 写 1，无变化 |
| `battery/en_uisoc_ht_int` | 写 1，无变化，电量照样 70→71 继续充 |
| `battery/uisoc_ht_int_gap` | 同上（这两个是 `--w-------` 只写节点，读不出来） |

### 【四类】驱动层不可写 —— `-w` 显示可写但实际 `Permission denied`

```
/sys/class/power_supply/cp_master/online
/sys/class/power_supply/cp_slave/online
/sys/devices/platform/pd_cp_manager/request_ibus
```

**这三个是最可惜的** —— 如果能直接让充电泵下线、或把泵的请求电流置 0，
就能一步做到真旁路，完全不用绕 `enable_sc`。驱动层把这个口子挡掉了。

### 【五类】本机不存在

```
/sys/class/power_supply/battery/batt_slate_mode    （Pixel 专用）
/sys/class/power_supply/battery/store_mode         （Pixel 专用）
```

> 这两个是 Pixel 那套「商店模式」，会**真正断开电池**，拔充电器直接关机。
> 社区模块 QSC 的候选表里有它们，**本机没有，而且就算有也不建议常驻使用**。

### 2.1 采样原始数据（换充电器过程，每 5 秒一条）

### 2.2 两边的差异

| | 电脑 USB 口 | 原装充电头 |
|---|---|---|
| `usb/real_type` | `Unknown` | `USB_PD` |
| `usb/input_current_now` | 约 410 mA（准确） | **0**（电走泵，测不到） |
| `cp_ibus` | 1～3（泵基本不动） | 267 → 579（泵全速） |
| 电流路径 | 主开关充电器 | **充电泵**，绕开主充电器 |
| `current_cmd="0 1"` | ✅ 有效 | ❌ 无效 |

## 三、找到解法：MTK Smart Charging

### 3.1 第一次偶然发现（`sc_tuisoc` = 当前电量）

```
当前电量 = 88
=== 设 sc_tuisoc=88，enable_sc=1 ===
  sc+0s    cap=88 ibat=-1880000  cp_ibus=701  usb_on=1  enable_sc=1
  sc+10s   cap=89 ibat=-1808000  cp_ibus=679  usb_on=1  enable_sc=1
  sc+20s   cap=89 ibat=+534000   cp_ibus=1    usb_on=1  enable_sc=1   ← 停充
  sc+30s   cap=89 ibat=0         cp_ibus=3    usb_on=1  enable_sc=1   ← ★ 电池闲置
  sc+45s   cap=89 ibat=0         cp_ibus=1    usb_on=1  enable_sc=1   ← ★ 保持
  sc+60s   cap=89 ibat=0         cp_ibus=1    usb_on=1  enable_sc=1   ← ★ 保持
```

配套 dmesg（框架没有把它改回去）：

```
[smartcharging] [sc1]en:1 t:0,80000,... c:0,2000 ibus:0 uisoc:89,88 s:3000 ans:disable
[enable smartcharging] : 1
[smartcharging target uisoc] : 88
```

`en:1`（启用）、`c:0`（充电电流 0）、`uisoc:89,88`（当前 89，目标 88）。

**从写入到 `ibat=0` 用了约 20～30 秒。**

### 3.2 为什么最初误判它无效

第一次测 `enable_sc` 时，**观察窗口只给了 10 秒**：

```
=== MTK 智能充电 ===
    enable_sc : [0] -> [1]
  写入后 10s    cap=87 ibat=-1914000  cp_ibus=692  usb_on=1   ← 只降了 20%，看着像"没用"
  已还原        cap=88 ibat=-2261000  cp_ibus=726  usb_on=1
```

当时的结论是「只让电流轻微下降，无效」。**实际它需要 20～30 秒才收敛。**
差 20 秒，把唯一有效的机制扔了，导致多绕了一整轮。

> **教训：对充电器状态机的实验，观察窗口不要短于 45 秒。**

## 四、电脑 USB 口的 90 秒持续验证

**目的**：证明 `current_cmd="0 1"` 在非充电泵路径下确实能让电池闲置，且能长期保持
（排除「电量计读数卡住」的可能）。

```
屏幕: mWakefulness=Asleep

=== 基线（night_charging 保持 0）===
  t=0   night=0 cap=72 status=Charging current_now=-405000 input_suspend=0 ccl=0
  t=5   night=0 cap=72 status=Charging current_now=-402000 input_suspend=0 ccl=0
  t=10  night=0 cap=72 status=Charging current_now=-451000 input_suspend=0 ccl=0

=== 写入 current_cmd = '0 1'，保持 90 秒 ===
  t=0   cap=72 status=Charging current_now=-386000 usb_in=160  pmic_ibat=2
  t=15  cap=72 status=Charging current_now=0      usb_in=47   pmic_ibat=2   ★
  t=30  cap=72 status=Charging current_now=0      usb_in=112  pmic_ibat=2   ★
  t=45  cap=72 status=Charging current_now=0      usb_in=37   pmic_ibat=2   ★
  t=60  cap=72 status=Charging current_now=0      usb_in=110  pmic_ibat=2   ★
  t=75  cap=72 status=Charging current_now=0      usb_in=32   pmic_ibat=2   ★
  t=90  cap=72 status=Charging current_now=0      usb_in=82   pmic_ibat=2   ★

=== 还原 current_cmd = '0 0' ===
  t=0   cap=72 ibat=0        usb_in=410
  t=5   cap=72 ibat=-451000  usb_in=410   ← 立即恢复充电
```

关键点：
- **`current_now` 持续 6 次采样精确为 0**（15 秒间隔），`pmic_ibat=2`（≈0）
- `usb_in` 随系统负载浮动（32～160 mA）—— 证明是**适配器在给系统供电**
- 电量全程 72 不动
- `battery/status` 仍显示 `Charging`（驱动不更新这个字段，**不要用它判断**）

## 五、v10.x 阶段的真机验证（合规性修复）

这些是模块「基础正确性」的验证，与旁路机制无关，但值得知道已经验过。

### 5.1 KernelSU 安装路径

- KernelSU **从不执行模块 zip 里的 `META-INF/update-binary`**。
  `installer.sh` 用 `unzip -o "$ZIPFILE" -x 'META-INF/*'` 明确排除。
  实测：安装后模块目录里确实没有 `META-INF`。保留它只是为了 Magisk 兼容。
- `customize.sh` 被 **source** 执行（不是 exec），`$MODPATH` 可用。
- KernelSU 默认把模块内文件设为 **0644**，所以 `customize.sh` 里对这 4 个脚本显式 chmod 0755。
  实测安装后：脚本 `-rwxr-xr-x`、`module.prop` `-rw-r--r--` ✅
- 模块注册状态：`enabled=true`、`update=true`、**`mount=false`**（无 `system/` 目录，不需要 metamodule）。
- `web` / `action` 标志只在文件位于 **active 目录**后才是 true（`list_module` 只查 `/data/adb/modules`，
  不查 `modules_update`），所以**重启前看不到 WebUI 入口是正常的**。

### 5.2 卸载时旧模块目录被整体替换

`module.rs` 的 `handle_updated_modules()`：

```rust
if module_dir.exists() {
    remove_dir_all(&module_dir)?;      // ← 整个旧目录被删掉
}
rename(updated_module, &module_dir)?;
```

**结论：用户写在模块目录里的配置一定会在更新时丢失。**
所以本项目的配置放在 `/data/adb/bypass_charger/`（模块目录之外）。

### 5.3 SELinux

- 写入 `night_charging`（`u:object_r:sysfs_battery_supply:s0`）从 `u:r:ksu:s0`
  **没有任何 avc 拒绝**，**不需要 `sepolicy.rule`**。
- 日志里能看到的 avc 拒绝都来自 `health@2.1-serv` / `system_app` 等 ROM 自带组件，与本模块无关。

### 5.4 逻辑测试（假 sysfs，真机 shell）

用假 sysfs 目录跑了 6 个用例，全部通过：

| 用例 | 结果 |
|---|---|
| 正常阈值切换（95→开、50→关、99→开） | ✅ |
| 无配置文件 → 生成默认值，且开机落在阈值之间不动作 | ✅ |
| 配置文件注入尝试（`ENABLE_THRESHOLD=90; touch PWNED`） | ✅ 被中和（值截取为 90，配置不被 source 执行） |
| 非法阈值（ENABLE ≤ DISABLE） | ✅ 回退默认并记 WARN |
| 单实例保护 | ✅ 第二个实例静默退出 rc=0 |
| 控制节点不存在 | ✅ 优雅告警，不崩溃 |

### 5.5 测试过程中抓出的真实 bug（都已修）

1. **`trap` 里没有 `exit`** —— 收到 SIGTERM 后处理函数跑完，shell 会**回到主循环**继续跑，
   进程永远杀不掉。（第一次跑功能测试就是这么卡死的。）
2. **直接 `sleep 60` 不可中断** —— shell 会阻塞等待子进程，SIGTERM 要等这一轮睡完才生效。
   改成 `sleep N & wait $!` 后可立即响应。
3. **PID 文件写在了目录创建之前** —— 首次安装后状态目录还不存在，
   `echo $$ > "$PID_FILE"` 静默失败，导致单实例保护、`action.sh`、`uninstall.sh` 三处全失效。
   这个 bug 是**用户重启设备后看日志才发现的**（`daemon.pid` 不存在）。
4. **`< file` 重定向的 stderr 拦不住** —— `tr ... < "$f" 2>/dev/null` 里，
   重定向由 **shell 本身**执行，`2>/dev/null` 挂在命令上没用。
   改成 `cat "$f" 2>/dev/null | tr ...`。
5. **状态判定不该看电池电流** —— 原逻辑用「`ibat == 0`」判断是否旁路，
   在供电不足的适配器（电脑 USB 口）下永远显示「正常充电」。
   改成以**控制节点的实际值**为准。
6. **缓存状态不可信** —— 守护进程原来只信自己记的状态，不重读节点。
   MIUI 框架会改写 `enable_sc`，驱动也可能在插拔充电器时重置节点。
   加了每轮 `state resync`。

### 5.6 一个排查教训

一度以为出现了**两个守护进程**（pid 1538 和 9177）。实际是
**busybox 在 standalone 模式下 fork 后不 exec，`nap()` 里的 `sleep` 子进程继承了父进程的 cmdline**，
所以 `/proc/PID/cmdline` 看起来一模一样。65 秒后旧 pid 消失、新 pid 出现，正好对上 60 秒周期。

> **按 cmdline 扫 `/proc` 会误判**，排查重复进程要看 `ppid` 和 `wchan`。
> 另外之前用 `ps -o NAME` 查残留也是假阴性 —— `sh script.sh` 的进程名只显示 `sh`。

### 5.7 无线调试 + 热更新流程（Windows 环境）

- `adb tcpip 5555` 可在 LAN 上开一个传统免配对端口；
  系统自带的无线调试用随机端口（本项目当时是 39829）。
- **重启 adbd 会让系统重新分配无线调试端口**（当时变成 37903）。
- 本机环境**每次重新执行命令都会重启 adb server**，所以每条命令前都要 `adb connect`。
- 热更新流程见 `README.md` 第四节。

## 九、v11.5 真机验证记录（双状态显示 + 修掉缓存失同步）

### 9.1 改动的动机

v11.4 上线后用户反馈两点：

1. **「旁路是否开启」的状态没了。** v11.4 把两个状态做成了**互斥**
   （`usb/online == 0` 就整条显示「未接充电器」，把旁路状态盖掉）。
   而 `current_cmd` 是持久的，拔线后它仍然是 `0 1`，用户需要看到这一点。
   **正确做法是两个状态同时显示，互不覆盖。**
2. **路径没有写明「路径」两个字。** 原来只是把目录直接跟在后面。

设备上确认了问题：

```
usb/online  = 0        current_cmd = [0 1]（旁路状态是开着的）
介绍栏      = ○ 未接充电器 · 配置 config.sh · 日志 run.log · /data/adb/bypass_charger/
              ↑ 旁路状态不见了
```

### 9.2 修法

| 文件 | 改动 |
|---|---|
| `moduledesc.sh` | 两个状态独立计算后拼接：`$(bypass_head $1) · $USB_HEAD`，不再互斥；文案加上「路径」二字 |
| `webroot/index.html` | 徽章只能显示一个状态，所以**另起一行常驻显示「旁路」**，避免被充电器状态盖掉 |
| `moduledesc.sh` | **移除 `.desc.last` 缓存**（见 9.4） |

### 9.3 分支穷举（6 个组合全过）

```
usb=1      旁路=on   -> ● 旁路已开启 · 已接充电器 · 配置 config.sh、日志 run.log · 路径 ...
usb=1      旁路=off  -> ○ 旁路未开启 · 已接充电器 · 配置 config.sh、日志 run.log · 路径 ...
usb=0      旁路=on   -> ● 旁路已开启 · 未接充电器 · 配置 config.sh、日志 run.log · 路径 ...
usb=0      旁路=off  -> ○ 旁路未开启 · 未接充电器 · 配置 config.sh、日志 run.log · 路径 ...
usb=读不到 旁路=on   -> ● 旁路已开启 · 充电器状态未知 · 配置 config.sh、日志 run.log · 路径 ...
usb=读不到 旁路=off  -> ○ 旁路未开启 · 充电器状态未知 · 配置 config.sh、日志 run.log · 路径 ...
```

**穷举方法**（比 v11.4 那次更可靠）：不去 sed 插入 echo，而是把脚本副本的
`USB_ONLINE_FILE` 指向假文件，再用 `BYPASS_CHARGER_STATE_DIR` 把状态目录隔离到临时目录，
直接**读脚本自己写出的 `.desc.last`** 看它算出了什么。省掉了插桩，不会再出现
sed 没生效导致测试"假通过"的情况。

### 9.4 穷举测试意外抓到的真 bug：缓存失同步

穷举跑完后的「恢复成真实状态」那一步失败了，介绍栏残留着测试用的临时路径：

```
override.description=○ 旁路未开启 · 充电器状态未知 · ... · 路径 /data/local/tmp/dtest/
```

**原因**：`.desc.last` 缓存保存的是「上次写出去的文字」，它**和真实的
`override.description` 是两个地方**。当时真实缓存里已经是正确的文字，
而恢复时算出的文字又恰好和缓存一致 → 脚本 `exit 0` **根本没去改配置** →
残留值就留下来了。

**这在生产里会真实发生**：

- 跑了 `ksud module config clear`，或重装模块（`clear_module_configs` 会清配置），
  但 `.desc.last` 在模块目录之外、**活得比配置久** → 缓存说"已写过"，
  配置其实是空的 → 介绍栏**永远修不回来**
- 别的工具/人手动改过 `override.description` → 同理

**修法**：去掉缓存，每次都写。调用频率本来就极低（见 7.4），
省这一次进程创建不值这个风险。`.desc.last` 保留但降级为**排查用的记录**，不参与判断。

### 9.5 自愈验证

```
先故意把介绍栏写坏（模拟配置被外部清空/改乱）
  现在 -> [被写坏的文字]
跑一次 moduledesc.sh
  现在 -> [● 旁路已开启 · 未接充电器 · 配置 config.sh、日志 run.log · 路径 /data/adb/bypass_charger/]
```

修复后能自动纠正被写坏的配置 ✔ —— 这在旧版（有缓存）下是做不到的。

### 9.6 一条教训

**缓存类优化要先确认被优化的那个开销真的存在。** 这次的缓存是为了避免
「`status` 每 3 秒调一次 ksud」，而实际上 `status` 根本不调它。
凭想象引入的优化，只带来了失同步的风险。而且这个 bug 还是**测试跑完后的清理步骤
失败**才暴露出来的 —— 如果测试只关注"6 个分支对不对"，就会漏掉它。

## 十、v11.7 省电优化：全部实测数据

**目标：不改变任何功能**（DEBUG 保持 1、日志格式不变、阈值逻辑不变、WebUI 输出不变）。

### 10.1 先测出钱花在哪

采样 180 秒（3 个 tick），读 `/proc/PID/stat` 的 `utime+stime+cutime+cstime`
（含子进程，单位 jiffy = 10ms）：

```
优化前:
  守护进程自身 CPU :  70 ms
  子进程 CPU 合计  : 910 ms      ← 93%
  合计             : 980 ms  →  327 ms / tick  →  约 406 秒 CPU / 天
```

**93% 在"创建子进程"**，所以瓶颈是 fork 次数，不是脚本逻辑。

### 10.2 单次调用成本（每种 60 次平均）

```
$(cat f | tr -cd '0-9')                          32 ms
$(cat f | tr -s ' \t' ' ' | sed 's/^ *//; s/ *$//')   47 ms
$(date +%s)                                      20 ms
$(wc -c < f)                                     19 ms

纯内建运算                                       ~0 ms
```

顺便确认了这台设备的 `/system/bin/sh` 是 **MIRBSD KSH R59 (Android)**，
`[`、`test`、`echo`、`case`、`$(())`、参数展开**全是内建**，不 fork。
（这一点值得记：一开始怀疑 `[` 是外部命令，实测排除了。）

### 10.3 改了什么（功能零变化）

| 位置 | 原来 | 现在 |
|---|---|---|
| 守护进程每轮读电量 | `$(cat \| tr -cd '0-9')` | `read` 内建（`read_digits_val`） |
| 守护进程每轮读状态节点 | `$(cat \| tr -s \| sed)` | `read` 内建 + 罕见回退（`read_control_state`） |
| 守护进程每轮算冷却 | `$(date +%s)` | **轮数计数器**（`tick_no` / `COOLDOWN_TICKS`） |
| 自愈判定的两次读 | 2 × `$(cat)` | `read` 内建，且 ibat 复用本轮已读值 |
| DEBUG 日志行里的 4 次读 | 4 × `$(cat)` | `read` 内建预读 |
| `log()` 日志轮转 | 每条都 `wc -c` | 每 32 条查一次（最坏多 2KB 才轮转） |
| `log()` 权限 | 每条都 `chmod 600` | 只在文件新建/轮转后做一次 |
| `status` 的 8 次读数 | 8 × `$(cat)` | `read` 内建 |
| `status` 的 4 个配置键 | 4 × `$(sed\|tr\|head)` = 12 个进程 | `conf_val` 纯内建 while-read |
| `status` 的版本号 | `$(sed \| head)` | `module_version` 纯内建 |
| `status` 的守护进程 pid | `$(daemon_pid)` 子 shell | `daemon_pid` 写全局变量 |

### 10.6 剩下的开销（属于固有成本）

```
76 ms/tick 的构成（估算）:
  log() 里的 date（日志时间戳）    ← DEBUG=1 每轮一条，必须有
  nap() 里的 sleep（可中断等待）    ← 去掉就没法快速响应 SIGTERM
  守护进程自身的 shell 开销         ← 解析/内建/循环
```

想再降只能：**关掉 DEBUG**（用户明确要求保留）或 **调大 `CHECK_INTERVAL`**
（会降低响应速度）。这两个都不属于"不改功能"。

### 10.7 两个必须记住的 `read` 内建坑（实测）

**坑 1：`read` 失败时不会清空变量。**

```
read -r v < /no/such/file   →  v 保留上一次的值，返回值 1
```

所以必须 `v=""; read -r v < "$f"`。少了置空就会拿旧值去比阈值。

**坑 2：`read` 不折叠内部连续空白。**

```
原文 "0 1"      read=[0 1]      cat|tr|sed=[0 1]      一致
原文 "0  1"     read=[0  1]     cat|tr|sed=[0 1]      ★不一致★
原文 "  0 1"    read=[0 1]      cat|tr|sed=[0 1]      一致（前导空白会去掉）
原文 "   0   1" read=[0   1]    cat|tr|sed=[0 1]      ★不一致★
```

状态判定是字符串比较（`"$v" = "$STATE_STOP"`），所以多空格会让判定失效。
解决：常见路径内建直比，比不中才回退老写法；但**空值不要回退**。

## 十一、v11.10 真机监控：查出「守护进程被冻结」并修正充电泵结论

### 11.1 起因

用户把阈值改成 80/75 并插上充电器，让我监控。结果**模块没有进入旁路**，
电量从 81% 一路充到 88%，而 `current_cmd` 一直是 `[0 1]`（旁路已下达）。

### 11.2 排查：守护进程被 cgroup 冻结

```
pid=11209  cmd=[sh .../auto_bypass.sh]
   state=S  ppid=1  wchan=do_freezer_trap     ← 关键字
   utime+stime=45（自 15:33 起不再增长）

cgroup 对照:
  冻结的守护进程  = 0::/uid_10228/pid_8304   ← 管理器 App 的 cgroup
  从 adb 启动的    = 0::/                     ← 根 cgroup
```

`do_freezer_trap` = 进程在**被冻结的 cgroup** 里。原因是用户在 **WebUI 里改配置
并点「保存并重启」**，新守护进程继承了管理器 App 的 cgroup，用户离开管理器后
Android 把整个 cgroup 冻住 —— 守护进程静默停摆（日志不写、阈值不触发），
而 `pgrep` 还能找到它、`ps` 显示 `S`，**看起来完全正常**。

**修法已验证可行**：

```
测试进程 pid=19442  初始 cgroup: /
已移入 uid_10228          （echo pid > /sys/fs/cgroup/uid_10228/cgroup.procs）
现在 cgroup: /uid_10228
移回根 cgroup: 成功        （echo pid > /sys/fs/cgroup/cgroup.procs）
最终 cgroup: /
```

**修复后的端到端验证**（模拟 WebUI 场景：包装脚本先把自己移进 `uid_10228`，再 exec 守护进程）：

```

  初始 cgroup = /
  移入后 cgroup = /uid_10228
  exec auto_bypass.sh ...
新守护进程 pid=23697   cgroup = /
日志: debug: cgroup=/uid_10228 -> /（非 / 会被系统冻结）
```

### 11.3 ⚠️ 修正一个之前下错的结论：`constant_charge_current=0`

监控后段我做了一批「能否真正关掉充电泵」的节点测试。第一轮结果里有两条
**看起来成功了**：

```
基线:                          ibat=-1031000   cp_ibus=578   usb_on=1
C. constant_charge_current=0 → ibat=  +43000   cp_ibus=  1   usb_on=1
F. enable_meta_current_limit=0 → ibat= +119000  cp_ibus=  3   usb_on=1
```

**但这是假象。** 同一时刻 MTK 智能充电正好自己生效了（`ans:ignore` → `ans:disable`），
我把这个巧合归因给了那个节点。

决定性实验：先主动关掉智能充电（`enable_sc=0` + `sc_tuisoc=95`）**逼出全速快充**，
确认基线成立后再单独写该节点：

```
基线（已确认全速充电）: ibat = -1465000
写入 constant_charge_current = 0，观察 3 分钟:
  +10s  ibat=-1446000   +40s ibat=-1442000   +80s ibat=-1450000  cap 89→90
  +120s ibat=-1491000   +150s ibat=-1446000  +180s ibat=-1393000
  ← 整整 3 分钟毫无作用，电量还在涨
```

**结论：`constant_charge_current=0` 无效。** `enable_meta_current_limit=0` 出自同一批
测试、很可能是同一个巧合，我没有重测，一并标注为**可疑、不要采信**。

> 教训：**单次实验里同时存在两个变化量时，不能把结果归因给其中任何一个。**
> 这次是"我写的节点"和"MTK 自己生效"同时发生。做这种测试必须先把无关变量
> 明确排除掉（这次是先把智能充电关掉逼出稳定基线），否则很容易得出错误因果。

### 11.4 修正后的完整机理

把两轮测试合起来看，真正的分界线是**充电泵是否在工作**：

| 充电泵 | `cp_ibus` | 典型 `ibat` | 内核回答 | 旁路能否生效 |
|---|---|---|---|---|
| 全速（PPS 快充） | 500～1100 | -2 ～ -3 A | `ans:ignore` | ❌ **不能** |
| 闲置（主充电器路径） | 1～3 | -1.5 A 或 0 | `ans:disable` | ✅ **能** |

依据：

```
泵全速时:
  [smartcharging] [sc1]en:1 ... c:-2853,2000 ... uisoc:84,80 ... ans:ignore
  写入 current_cmd / enable_sc 两段式后 3 分钟，ibat 仍在 -2~-3A

泵闲置时:
  [smartcharging] [sc1]en:1 ... c:0,2000 ... uisoc:89,80 ... ans:disable
  ibat=0 稳定
```

`current_cmd` 和 `enable_sc`（MTK 智能充电）**都只控制主开关充电器**；
PD 快充时电流走充电泵、绕开了主充电器，所以两者都无效。
能直接关泵的三个节点（`cp_master/online`、`cp_slave/online`、
`pd_cp_manager/request_ibus`）在第三节已记录 —— `-w` 显示可写但实际 `Permission denied`。

### 11.5 实际影响（用户需要知道）

**旁路生效点会比设定阈值高。** 本次实测：

```
阈值设 80%   → 80~88% 期间仍在全速快充（泵在跑）→ 旁不了
               到 90% 泵停了 → 才真正进入旁路，之后稳在 90%
```

所以最终稳定点是 **90% 而不是配置的 80%**。这不是 bug，是硬件/驱动的限制，
但这里必须讲清楚，否则接手人会以为是阈值逻辑写错了。

### 11.6 修复后的稳定验证

```
16:03:29 → 16:05:22（13 次采样，每 10 秒）:
  cap=90  byp=on  idle=1  ibat=0  uon=1  uty=USB_PD  cp=1~3   uin=147~627 mA
  （13 次里 12 次 idle=1，另一次读 6000 = 6mA，可忽略）

status:
  BYPASS=on   BYPASS_EFFECTIVE=1   IBAT_IDLE=1   USB_ONLINE=1   CP_IBUS=1
守护进程: cgroup=/ -> /（修复生效）
```

这是**真旁路**：电池不充不放、适配器给手机供电、PD 协议挂着、充电泵关闭。

### 11.7 本次还修的两个小问题

**① 状态误导（新增 `BYPASS_EFFECTIVE`）**

`BYPASS=on` 而电池在 2A 充电时，WebUI 徽章原本显示"旁路已开启"。
现在分开报：

```
BYPASS=on              ← 状态节点写进去了
BYPASS_EFFECTIVE=0     ← 但电池其实还在充（判据与守护进程的 bypass_ineffective 一致）
```

WebUI 徽章相应新增「旁路无效」（红色）分支。

**② v11.7 引入的首轮自愈延迟（回归）**

v11.7 改成轮数计数器后：`1 - 0 >= 2` 不成立 → 要等第 2 轮。
日志证实了这次确实等到第 2 轮（15:38:21 启动，15:39:21 才重打）。

修法：把 `last_apply_tick = 0` 当作「本次启动后还没重打过」，不受冷却限制。

> 这条是 v11.7 声称「功能零变化」时**漏掉的行为差异** —— 记录在此以免再犯。

### 11.8 一个没还原干净的小遗留

## 十二、v11.11 精简：证明「两段式」是多余的

### 12.1 起因：用户的两个质疑

> 咱们自己设置的充电阈值完全没用，miui 智能充电到 90% 开启，跟我设不设置问题不大，
> 而且我觉得恢复充电的值有没有都不影响，可以去除

两个判断要分开验证。结论是**第一个被推翻、第二个一半对**。

### 12.2 判断一被推翻：停充确实是模块干的

**实验 A（第一次，被污染、作废）**：没停守护进程做 A/B。
结果守护进程中途自己把 `current_cmd` 从 `[0 0]` 改回 `[0 1]`，
两个变量的效果混在一起，无法判定。

> 教训：**做这种实验必须先把守护进程停掉**，否则它在背后改同一个节点。

**实验 B（决定性）**：停掉守护进程，并把 `enable_sc=0`、`sc_tuisoc=95`
（两个设置都远离模块配置 —— MIUI 智能充电完全不参与）：

```
基线（已确认全速充电）  ibat = -1439000
只写 current_cmd=0 1 → ibat = 0           持续 60 秒
只写 current_cmd=0 0 → ibat = -1359000    立刻恢复全速充电

dmesg: [smartcharging] [sc1]en:0 ... c:-1374,2000 ... ans:ignore
       ↑ en:0（智能充电是关的），但电流从 -1374 变成 0
         → 停充是 current_cmd 干的，与 MIUI 无关
```

**结论：`current_cmd` 单独就能停充和恢复充电。用户的判断一被推翻。**

### 12.3 判断二一半对：恢复的值不能去，但旁边两条可以

先进入稳定的旁路闲置态，然后只写一条，看充电何时恢复：

```
进入旁路闲置（cmd=[0 1]，电流 0，enable_sc=0，sc_tuisoc=80）
只写 current_cmd = 0 0:
  +5s   ibat=-1435000     ← 立刻就恢复了
  +40s  ibat=-1295000
```

**`current_cmd="0 0"` 单独就能恢复充电，它是必需的那一条，不能去。**

把它和实验 B 合起来看，得到更彻底的结论：

| 动作 | 原以为的角色 | 实测结论 |
|---|---|---|
| `current_cmd=0 1` / `0 0` | 维持手段 | ✅ **必需**，唯一真正干活的 |
| `enable_sc` 0→1 | 「打断 PD 快充」 | ❌ 多余。泵全速时没用（重打 3 次全失败），泵闲时也不需要 |
| `sc_tuisoc=@THRESHOLD`/`@SC_ORIG` | 「告诉 MTK 目标电量」 | ❌ 多余。阈值恰好等于原值 80 时是纯空操作 |

**整个「两段式」都是多余的。**

### 12.4 这是第二次「把 current_cmd 的功劳记到别人头上」

上一节刚记录过一次同类错误（`constant_charge_current`）。
这次是同一个毛病的另一面：**两段式当初被"验证有效"，是因为验证时
`cp_ibus=1`（泵闲着）—— 那时 `current_cmd` 单独就够，功劳被分给了旁边的动作。**

> 两次都指向同一个方法论问题：**没有隔离无关变量就下因果结论。**
> 正确做法是先构造一个「其他变量都不参与」的干净状态
> （这次是 `enable_sc=0` + `sc_tuisoc=95`），再单独改变待测变量。

### 12.5 精简后的验证

```
真机 sh -n:  auto_bypass.sh / bypassctl.sh / uninstall.sh / nodes.conf   全部 OK

bypassctl.sh off:  1 个动作，耗时 1 秒  → ibat=-1382000（充电恢复）
bypassctl.sh on:   1 个动作，耗时 1 秒  → ibat=0（电池闲置）

动作前: enable_sc=1  sc_tuisoc=80
动作后: enable_sc=1  sc_tuisoc=80      ← 两个节点完全没被动过 ✅

status: BYPASS=on  BYPASS_EFFECTIVE=1  IBAT_IDLE=1  CAPACITY=92
日志 : 不再输出 sc_orig=
```

从 4 个写入 + 4 秒变成 **1 个写入 + 1 秒**。

### 12.6 没能改变的部分

**充电泵的限制依旧**（见 11.4）：泵全速时（约 80~88%）旁路无效，
泵停后（约 89%+）`current_cmd` 才接管。

精简只是去掉了没用的动作，**没有也不可能解决泵的问题** ——
那三个能直接关泵的节点依然 `Permission denied`。

所以用户观察到的「90% 才停」依然成立，只是原因现在完全清楚了：
**不是阈值没用，是泵在挡路。**

### 13.6 「双实例」虚惊：busybox ash 的 NOFORK 子进程会继承父进程 cmdline

**现象**：`pgrep -f auto_bypass` 一次返回 **4 个 pid**（1568 / 9281 / 9488 / 9490）。
如果真有多个守护进程，它们会互相抢写 `current_cmd`，是个必须查清的问题。

**排查**：连续采样 + `ps -A -o pid,ppid,args` 看 ppid，结论是虚惊：

| pid | ppid | 真身 |
|---|---|---|
| 1568 | 1 | ✅ 真正的守护进程（只有这一个） |
| 9488 / 9490 | — | adb shell 链路自身 —— 它的 cmdline 里就含 `auto_bypass` 字样，`pgrep -f` 自匹配 |
| 9281 / 9898 / 13790 / 16809 | **1568** | 守护进程的子进程：`comm=(busybox)`、`wchan=__arm64_sys_nanosleep`、存活约 60 秒 = `nap()` 里的 `sleep 60 &` |

**根因**：这台机器的 `sh` 是 **busybox ash**（`/proc/<pid>/comm` 全都是 `busybox`），
而 `sleep` / `cat` / `tr` / `date` / `sed` / `wc` 在 busybox 里是 NOFORK/NOEXEC applet ——
**它们 fork 之后不再 exec**，于是子进程的 cmdline 和 comm 与父 shell 一模一样。
所以"数 cmdline 命中条数"这个判断方法在这台机器上**天然多报**。

对代码的实际影响（记下来，免得以后误判成 bug）：

- `bypassctl.sh` 的 `daemon_pid()` 会命中这些子进程，但**子进程 pid 必然大于父进程**，
  而它是按 /proc 数字升序扫的，所以先命中的仍是真守护进程 —— **当前安全**。
  （只有 PID 回绕时才可能破，概率极小，不作为当前问题。）
- `restart` 里的 `kill -9` 循环会顺手把 `sleep` 子进程也杀掉，无害。
- **结论：不要用 `pgrep -f` 的命中条数数实例个数，要看 ppid（真守护进程 ppid=1）。**

## 十四、二类（停充）节点逐个实测 —— 含「泵全速」这个关键窗口

> 时间：2026-10-06 17:07–17:31　条件：原装充电头 PD、电量 87→91%
> 方法：**先停守护进程**（§12.2 的教训），每项都从"确认正在充电"的基线开始，
> 结束后确认"已恢复充电"再进入下一项。脚本 `tests/停充实测脚本.sh` / `2.sh` / `3.sh`。

### 14.1 结论表

| 节点 | 写入 | 干净基线（主充电路径） | **泵全速下** | 判定 |
|---|---|---|---|---|
| `battery/input_suspend` | `1` | `ibat` 转正 **+43~+760 mA**，`usb/online`→0 | `cp_ibus` **598→1（约 5 秒）**，`ibat` 转正 +43~+119 mA | ✅ **停充有效，且不受充电泵限制** |
| `usb/input_suspend` | `1` | `ibat` 转正 **+190~+790 mA**，`usb/online`→0 | `cp_ibus` **571→3（立刻）**，`ibat` 转正 +190~+236 mA | ✅ **停充有效，泵下反应最快** |
| `battery/night_charging` | `1` | **`ibat=0` 且 `usb/online=1`、`usb_in=162~265 mA`** = **真旁路** | 未测到（91% 时泵不肯介入，`cp` 一直是 1~3） | ✅ 有效，但**是真旁路不是停充**（复现 2 次） |
| `charger/input_current` | `100` | 只中断约 **10~15 秒**，随后 `usb_in=1575`、`ibat=-1.45 A` 全速恢复 | — | ❌ **基本无效** |
| `/proc/mtk_battery_cmd/en_power_path` | `0` | `usb_in`→0，`ibat` 转正 **+145~+198 mA** | 泵在跑时写 0 **不影响泵**（照充 1.83 A） | ⚠️ 有效但**驱动自管、不可靠** |

### 14.2 最重要的一条：停充节点**不受充电泵限制**

这是它相对 `current_cmd` 的**唯一优势**，也是本次才拿到的数据。

泵全速下（`cp_ibus≈570`、`usb_in=0`、`ibat≈-1.0~-1.1 A`）写 `battery/input_suspend=1`：

```
17:22:17 泵基线   ibat=-952000  usb_on=1 usb_in=0 cp=492
17:22:18 泵+写1   ibat=-952000  usb_on=0 usb_in=0 cp=598   ← 同一秒，还没反应过来
17:22:23 泵+写1   ibat=+726000  usb_on=0 usb_in=0 cp=1     ← ★ 泵停摆，电流转正
```

`usb/input_suspend=1` 更快（`cp` 571→3 在同一采样点内完成）。

**机理**：这两个节点切的是**电池输入路径**，泵没有可灌的负载，自然就停了；
而 `current_cmd` 管的是主开关充电器，泵绕开了它。**代价不变**：转为电池供电
（实测 +43~+790 mA 放电），低电量时会持续掉电。

对照组（同一时间窗）：`current_cmd=[0 1]` 而 `cp_ibus≈490~570` 时，
`ibat` 仍是 **-1.0~-1.5 A** —— 又一次现场确认 `current_cmd` 对泵无能为力。

### 14.3 推翻一条旧结论：`charger/input_current` 是无效的

从确认充电中的干净基线（`ibat=-1.42 A`、`cp=490`）写 `100`：

```
17:24:45 写100  ibat=-1710000  usb_in=0    cp=535
17:24:50 写100  ibat=+123000   usb_in=15   cp=3     ← 看起来"停充了"
17:24:55 写100  ibat=+179000   usb_in=15   cp=3
17:25:00 写100  ibat=-1472000  usb_in=1575 cp=3     ← ★ 全速恢复
17:25:05 写100  ibat=-1454000  usb_in=1575 cp=1
```

只中断了 **10~15 秒**，之后 `usb_in=1575 mA` —— **远超写入的限制值 100**，说明限制根本没生效，
那段中断只是 PD 重新协商的过渡。第一轮里测到的 `+390 mA`（§一 的表）**正是这个过渡窗口的读数**。

> 这是**第三次**同类错误：§2.3（`enable_sc` 只等 10 秒）、§11.3（`constant_charge_current`）、
> 本节。三次都是**观察窗口太短或没隔离无关变量**。45 秒下限必须守住。

另外：还原写 `-1` 后**读回是 0**（§11.8 记过），但实测**不影响充电**
（本次收尾时 `input_current=0`，手机照常 -1.4 A 充电）。驱动后来会自己重置成 -1。

### 14.4 `battery/night_charging` 复测到的是「真旁路」，不是停充

干净基线（`ibat=-1.50 A`、`usb_in=1575`）下写 `night_charging=1`：

```
17:25:57 写1   ibat=-1503000  usb_on=1 usb_in=1575 cp=1
17:26:02 写1   ibat=0         usb_on=1 usb_in=120  cp=1   ← ★ 电池闲置，适配器仍在供电
17:26:07 写1   ibat=0         usb_on=1 usb_in=157  cp=3
 ...（连续 8 个采样 ibat 精确为 0，usb_in 随负载浮动 120~250）
17:26:44 还原0 ibat=0         usb_on=1 usb_in=200  cp=1
17:26:49 还原0 ibat=-1423000  usb_on=1 usb_in=1567 cp=3   ← 立刻恢复充电
```

**`ibat=0` 且 `usb/online=1`、`usb_in` 随系统负载浮动 = 真旁路的判据**（§4 同一判据）。
17:29 在 91% 上又独立复现了一次（`cp=1`、`usb_in=247→162`、`ibat` 全程 0）。

这与 §一 表里的 `+488 mA`（停充）**不一致**。合理解释是 MIUI 的"夜间充电"语义就是
**暂停充电但由适配器继续给系统供电** —— 那本身就是真旁路。旧读数可能是泵/路径状态不同
或又落进了过渡窗口。**结论按"复现 2 次真旁路"记，但保留旧记录并在 §一 表上打了警告。**

⚠️ 仍未验：**91% 时叫不出充电泵**（PD 协商后仍是主路径 `cp=1~3`），
所以 `night_charging` 在泵全速下到底是真旁路、停充还是无效，**没有数据**。
要补的话得在 85% 左右（泵会介入的区间）做。

### 14.5 一个会坑到模块实现的坑：写入报错但**动作已生效**

三个 `power_supply` 类节点的写入**一律返回错误**，但**值都写进去了、动作也都发生了**：

```
> 写 [1] -> /sys/class/power_supply/battery/input_suspend
        rc!=0  读回=[1]  错误=[printf: write: Invalid argument]
```

`charger/input_current`、`current_cmd`、`en_power_path` 则**报错与行为一致**（成功就是成功）。

**对模块的直接影响**：`run_actions()` 用 `if echo "$val" > "$node"; then ... else log "ACTION FAILED"` 判断成败。
所以**备用方案 C1/C2/C3（正是这三个节点）一旦启用，会被模块误报为 `ACTION FAILED` 并返回 rc=1** ——
动作明明生效了。要用它们，**判断成败必须改成"读回节点值"**，不能看 `write` 的返回值。

### 14.6 顺手得到一个可复用的手法：把充电泵"叫回来"

`usb/input_suspend` 写 `1` → 等 6 秒 → 写 `0`，会触发 PD 重新协商，
**充电泵会重新介入**（本次复现 3 次：`cp` 从 1 → 506/712、403/585、493/568）。
在 88~90% 这个"泵快停了"的区间特别好用，是复现泵条件最省事的办法。

但注意：91% 时同法**叫不出泵**（电量越高、电池要的电流越小，PD 就不走泵了）。

### 14.7 本次踩的两个自己的坑（都不是设备问题）

1. **`/tmp` 在 Android 上不存在且根文件系统只读。** 脚本里写了 `2>/tmp/xxx` 之后，
   **重定向失败会让整条命令根本不执行**，而退出码只是 1、错误信息还落在别处 ——
   第二轮整轮 8 次写入全是空转，数据全废。**要写临时文件就写 `/data/local/tmp`。**
2. **把扫描 `auto_bypass.sh` 的循环内联进 `su -c '...'` 会自杀**：
   内联时 shell 自己的 cmdline 里就含 `auto_bypass.sh` 字样，`kill -9` 把自己也杀了
   （§13.6 同一个自匹配问题；模块的 `uninstall.sh` 注释里早就写过这点）。
   **这种循环必须放在脚本文件里跑**，因为文件的 cmdline 是 `sh /data/local/tmp/xxx.sh`。
   **而且不只是循环** —— 本次在同一个 shell 里又踩了一次：仅仅因为加了一句
   `echo "……auto_bypass.sh……"` 的提示文字，`bypassctl.sh restart` 的扫描就把整个 shell
   杀了（表现为输出在中途断掉、退出码 1）。**内联命令里只要出现该字样就会被命中。**
3. 附带：第一轮把 `en_power_path` 留在 `0`（误以为是它的原值），导致后面两项的基线一直是
   "已停充" —— 那两项判定作废，才有了第三轮的重测。
   **教训：每项测试后必须显式验证"已恢复充电"，再进入下一项。**

### 14.8 找到作者原版的原始帖子 —— 它和本节数据互相印证，并暴露我们漏了一步

做法出自酷安 @柳下惠77 的原帖。要点：

```
开：sh -c "echo 1 >/sys/class/power_supply/battery/night_charging" && chmod 440 该节点
关：chmod 660 该节点 && sh -c "echo 0 >/sys/class/power_supply/battery/night_charging"
"利用了手机的智能充电管理，夜间充电模式，达到80%后就停止充电变成旁路供电"
"能做到几乎0电流、电量不涨，随开随关"
"之前试过两个旁路充电模块都不好使，还是有500mAh 2w充电"
```

**三条互相印证 / 需要修正的地方：**

1. **印证了 14.4 的复测**：作者描述的正是"**几乎 0 电流、电量不涨**" —— 即**真旁路**
   （`ibat=0` 且适配器继续供电），和我们在 89% / 91% 两次测到的完全一致。
   → **§一 那张表里 `night_charging` 的「+488mA / 停充」是错的**，以本节为准。
2. **印证了"泵挡路"只对真旁路路径成立**：作者明确说"之前试过两个旁路充电模块都不好使，
   还是有 500mAh 2w 充电"—— 那 500mA/2W 正是**充电泵**在灌（`500mA × 4V ≈ 2W`，
   与 §2.1 采样到的泵电流量级一致）。而他用 `night_charging` 就绕过去了。
3. **⚠️ 我们漏了一步：帖子里有 `chmod`。**
   开的时候 `chmod 440`（把节点改成只读），关的时候先 `chmod 660` 再写 0。
   我们三次测试都**只写值、没做 chmod**，效果依然出现（45~60 秒窗口内）。
   推测 `chmod` 的作用是**把值锁住、防止 MIUI 的充电服务把它改回去**
   （节点属主是 `root:root`，`440` 让非 root 写入全部被拒）。
   **老记录里那个不一致的 `+488mA` 读数，很可能就是因为没 chmod 而被框架改回去了。**

**由此得到一个可检验的预测（正好用得上 70% 那次测试）：**

- 帖子说"**达到 80% 后**就停止充电变成旁路供电" → 它骑的是 MIUI 智能充电/夜间充电那套
  **以 80% 为界**的逻辑。所以：
  - **电量 ≥80%** 时写 `night_charging=1` → **立刻**转真旁路（我们在 89%、91% 都看到了）；
  - **电量 <80%** 时写它 → 可能**先继续充到 80% 才停**，而不是立刻停。
- 更重要的推论：泵全速的窗口是 **80~88%**，而 MIUI 恰好在 **80% 就停充** ——
  也就是说 **`night_charging` 有可能完全绕开充电泵问题**，而这正是 `current_cmd` 改不掉的那块。
  **这一条如果成立，它比当前用的 `current_cmd` 更强**（`current_cmd` 在 80~88% 完全无效）。
- 待验：**泵全速（80~88%）下 `night_charging=1` 到底是真旁路、停充还是无效** —— 无数据。

## 十五、★ 找到压下充电泵的办法：`night_charging`（2026-10-06 21:48–22:13 实测）

> 这是本项目**第一次拿到 80~88% 充电泵窗口里的真旁路**。
> 起因：用户提供酷安原帖（见 §14.8），随后把电量放到约 64% 再插原装头复测。

### 15.1 低电量下泵比 89% 时凶得多

```
21:47:36 cap=65 ibat=-3761000 usb_in=0 cp=1060
21:47:57 cap=65 ibat=-4693000 usb_in=0 cp=1250
21:48:26 cap=66 ibat=-5522000 usb_in=0 cp=1448   ← 峰值 -5.5A、cp=1448
```

对比 89% 时（`cp≈500`、`ibat≈-1.5A`）—— **泵窗口的负荷是 3~4 倍**。

### 15.2 九项测试的原始结论

| # | 测试 | 条件 | 结果 |
|---|---|---|---|
| A | `current_cmd=[0 1]` | 67%、`cp=1418`、`ibat=-5.3A` | ❌ **完全无效**（电流纹丝不动） |
| B | `battery/input_suspend=1` | 68%、`cp=1376` | ✅ `cp`→3（瞬间）、`ibat` 转正 |

| H | `en_power_path=1`（仅此一项） | 85%、`cp=621`、`ibat=-2.23A` | ❌ **杀不掉泵**（`cp` 仍 570~620、`ibat` 仍 -2.1A）；只让主路径也带上 ~130mA |
| I | `night_charging=1`（`en_pp` 已是 1） | 86%、`cp=585`、`ibat=-2.10A` | ✅★ 泵**立刻死**（`cp`→3），**`ibat=0` 连续 3 分钟**、`usb_in=127~265` 随负载浮动 = **真旁路** |

对照最干净的一组（同一分钟内）：

```
22:09:45 cap=86 ibat=-2117000 usb_in=107 cp=590  en_pp=1 cmd=[0 1]   ← cmd+en_pp 都拦不住
22:09:51 cap=86 ibat=-2098000 usb_in=172 cp=3    en_pp=1 cmd=[0 1]   ← 加一个 night=1，泵立刻死
22:10:06 cap=86 ibat=0        usb_in=132 cp=3    en_pp=1 night=1     ← 真旁路
   ...连续 12 条、跨 3 分钟，ibat 精确为 0，电量稳在 86% 不涨
```

### 15.3 三条硬结论

1. **`night_charging=1` 是唯一被证明能压下充电泵的机制**，但它**只在电量 ≥80% 时才起作用**
   （<80% 框架根本不理，照充到 80% 才停）。它骑的是 MIUI 智能充电/夜间充电那套以 80% 为界的逻辑。
2. **"停充"和"真旁路"的分界是 `en_power_path`**：
   - `en_power_path=0`（泵充电时驱动自动就是这个值）→ 系统转由**电池**供电 = **停充**；
   - `en_power_path=1` → 适配器接管系统供电 = **真旁路**（`ibat=0`）。
   - **但 `en_power_path=1` 自己杀不掉泵**（测试 H）—— 它只负责把"停充"升级成"真旁路"。
3. **`current_cmd` 在泵全速下彻底无效**，即使同时把 `en_power_path=1` 也写上（测试 A、H）。

### 15.4 由此得到完整的组合方案

三种场景各自的短板正好互补：

| 场景 | `current_cmd=0 1` | `night_charging=1` | `en_power_path=1` |
|---|---|---|---|
| <80%、主充电路径（5V 直充） | ✅ 有效 | ❌ 无效 | 把停充升级成真旁路 |
| **80~88%、泵全速** | ❌ **无效** | ✅ **压泵** | ✅ **让它变成真旁路** |
| ≥89%、泵已停 | ✅ 有效 | ✅（≥80 即有效） | 同上 |

**所以进入旁路时三条一起写，就能覆盖全部场景**：

```sh
printf '%s\n' '0 1' > /proc/mtk_battery_cmd/current_cmd                   # 主力：泵闲着时它干活
printf '%s\n' 1     > /sys/class/power_supply/battery/night_charging     # 压泵：≥80% 时框架立刻停充
printf '%s\n' 1     > /proc/mtk_battery_cmd/en_power_path                # 把"停充"变成真旁路
```

**退出时 `night_charging` 必须先写回 0**（否则框架会一直把充电保持在 80%、不再往上充）。

### 15.5 为什么 v11 反而丢掉了这个能力

原版 v9.9 用的**就是** `night_charging`（§14.8 的帖子 = v9.9 的方法）。
v11 换成 `current_cmd` 之后，代码更简单、可控、可回读、不依赖 MIUI 的调度，
**但把"压泵"这个能力丢掉了** —— 而压泵恰好是 `current_cmd` 唯一的死穴。

### 15.6 ⚠️ 待验与风险（别急着下结论）

1. **白天是否同样生效？** 本次全程在 **22:00 前后**，正落在 MIUI 夜间充电的时段里。
   `night_charging` 是"夜间充电"节点，**白天框架是否还理会它，必须白天复测一次**。
2. **长期保持**：MIUI 的夜间充电通常会在**早晨把电量补到 100%**。
   如果它自己恢复充电、而那时泵又在跑，`current_cmd` 是拦不住的。**需要过夜观察一次。**
3. **`chmod 440` 的必要性仍未证实**：§14.8 怀疑它是"锁住不被框架改回"的关键，
   但本次 3 分钟保持期内框架**没有**重置它；而 22:07:10 那次"被重置"经查是
   **我自己后台脚本的收尾**造成的假象（见 15.7）。所以 chmod 到底有没有用，目前无证据。
4. `en_power_path` 是**驱动自管**的节点（泵一起来它就自己变回 0），写它属于"顺手推一把"，
   不要指望它保持。

### 15.7 本次又踩的归因陷阱：后台脚本的收尾会污染手动实验

手动测 `night_charging` 时看到的"22:07:10 `night` 变回 0、充电恢复"，
我第一反应是"MIUI 把值重置了"。实际是**同一时间那个后台长跑脚本刚好命中退出条件、
它的收尾函数把 `night_charging` 写回了 0**。

> 教训：**长跑脚本与手动实验并行时，收尾动作会在你眼皮底下改节点。**
> 要么先停脚本，要么记住它的收尾时刻/动作再对照。这次是靠两份日志的时间戳才分辨出来。

### 15.8 `night_charging` 会被改回 0 —— 以及 v11.15 的"自愈 + 上锁"

**现象**：模块 22:20:04 写入 `night_charging=1`（日志有 `ACTION ok`），到 **22:36** 再读已经是 `0`。
中间**没有任何脚本或命令碰过它**（长跑脚本 22:07 就结束了；22:13 那次脚本收尾写的是 0，但之后
模块又在 22:20:04 写成了 1）。

**机制线索**：这个节点的属主和权限是

```
-rw-r--r-- 1 system system  /sys/class/power_supply/battery/night_charging
             ↑ 属主是 system
```

而 **MIUI 的充电服务就是以 `system` 身份运行的** —— 它拥有写权限，随时能把 1 改回 0。
这也正好解释了酷安原帖里那两步 `chmod`：`chmod 440` 去掉 owner 写位后，
`system` 身份就写不动了（它没有 `CAP_DAC_OVERRIDE`），而 root 照样能写。

**对照实验（22:37–22:52，脚本 `chmod假设验证.sh`）**：

| 阶段 | 条件 | 观察结果 |
|---|---|---|
| A | 只写 1，权限保持 644 | 5 分钟内**没有被改回** |
| B | 写 1 + `chmod 440` | 10 分钟内**也一直保持** |

**结论要如实说：我们没能复现"不加 chmod 就会被改回"，所以 chmod 不是已被证实的必要条件。**
它目前只能算"按作者原版的做法 + 机制上说得通"的保险。（A/B 都没出问题，也可能是那次改回
需要更长的时间或某个特定触发条件。）

**因此 v11.15 的做法是"自愈为主、上锁为辅"**：

1. **自愈（真正兜底，不依赖"谁改的"）**：守护进程每轮检查 —— 如果状态是旁路、
   但锁定节点（`LOCK_NODES`）的值不是 1，就以"旁路失效"的名义重打整个进入序列
   （与原来"电池还在充就重打"共用同一套冷却逻辑）。新增日志形态：
   ```
   bypass 失效（锁定节点已被改回），重打进入序列
   ```
2. **上锁**：`nodes.conf` 新增 `LOCK_NODES`；`write_node()` 写成功后按值处理 ——
   写 `1` → `chmod 440`（锁住），写 `0` → `chmod 644`（还原）。
   退出旁路与卸载（`uninstall.sh` 末尾）都会还原成 644，不会把 MIUI 的夜间充电永久挡在外面。

**真机验证（23:26）**：重启守护进程时 `night_charging` 正好是 0（前一个实验收尾写的），
守护进程第一轮就自愈了：

```
23:26:20 initial state=on
23:26:20 bypass 失效（锁定节点已被改回），重打进入序列
         printf: write: Invalid argument
23:26:21 ACTION note: night_charging 写报错(rc=1)但读回已是 '1'，按成功计
23:26:21   lock: chmod 440 /sys/class/power_supply/battery/night_charging（防止 MIUI 把它改回 0）
23:26:21 ACTION ok: '1' -> night_charging   (压在充电泵（≥80% 时框架立刻停充）)
23:26:22 ACTION ok: '1' -> en_power_path
→ 节点最终 night=1、权限 -r--r-----（已锁）
```

### 15.9 又一个小坑：busybox grep 的 `\|` 交替**不生效**

排查时用 `grep "锁定节点\|重打\|bypass ON"` 什么都搜不到，但单独 `grep 重打` 立刻命中。
同一天早些时候也踩过一次（`grep "input_current\|en_power_path"` 搜不到，其实文件里有）。

> 教训：这台机器的 `grep` 是 **busybox** 版，**别用 `\|` 做 BRE 交替**。
> 要多个模式就写 `grep -e A -e B`，或者分几次 grep。

### 15.10 一个反复踩的坑：内联命令里出现 `auto_bypass.sh` 字样 = 自杀

`bypassctl.sh restart` 和 `uninstall.sh` 都会扫 `/proc/*/cmdline`、把含 `auto_bypass` 的进程杀掉。
**内联 `su -c '...'` 时，只要命令文本里出现这个字样（哪怕只是一句 `echo` 的提示文字），
自己的 shell 就会被一起 `kill -9`** —— 表现是输出在中途断掉、退出码 1。

本次一天内踩了**三次**（§14.7 记了两次）。**涉及这个词的命令一律写成脚本文件再跑**
（文件的 cmdline 是 `sh /data/local/tmp/xxx.sh`，不含该字样）。

## 十六、v11.16：修掉 `chmod 440` 的死锁 + 补齐插拔状态机（2026-10-06 23:30–23:36）

### 16.1 ★ 一个只有真机才会暴露的自锁 bug

v11.15 的"上锁"是这样写的：**写值 → 成功后 `chmod 440`**。真机上第一次执行 `off` 就炸了：

```
退出旁路:
  FAILED: '0' -> /sys/class/power_supply/battery/night_charging   (写 rc=1 读回='1')
bypassctl.sh[300]: can't create /sys/class/power_supply/battery/night_charging: Permission denied
```

**`chmod 440` 之后连我们自己都写不进去** —— 节点被卡死在 `1`，`off` 彻底失效。
（如果没及时发现，手机重新插上后会被 MIUI 永久压在 80% 充不上去。）

**根因**：我们这个 ksu 的 root 上下文

| 能力 | 有没有 | 后果 |
|---|---|---|
| `CAP_FOWNER`（chmod 任意文件） | ✅ 有 | `chmod` 一直成功 |
| `CAP_DAC_OVERRIDE`（无视权限位读写） | ❌ **没有** | 往 440 的文件里写 → `EACCES` |

所以 `440` 对我们和 MIUI 是**一样的封锁**。酷安原帖写的是
"关的时候 **先 `chmod 660`** 再写 0" —— 顺序不是随便写的，就是绕这个。

**修法**：`write_node()` 改成 **先 `chmod 644` 解锁 → 写值 → 只有写 `1` 才 `chmod 440`**。
往返验证：

```
起点:        night=0 mode=-rw-r--r--
bypassctl on  -> ok: '1' -> night_charging    → night=1 mode=-r--r-----（已锁）
bypassctl off -> ok: '0' -> night_charging    → night=0 mode=-rw-r--r--（能写进去，还原成功）
```

**教训**：`chmod 440` 这种"防别人"的手段，**先确认自己还进得去**。
`-w` 测试（`[ -w "$node" ]`）在这种场景下更是骗人的 —— 它是 kernel 权限位判断，
而真正的写入被 `CAP_DAC_OVERRIDE` 的缺失挡在了下一层。

### 16.2 插拔状态机（v11.16 的第二件事）

**问题**：只要 `night_charging=1` 挂着，MIUI 就把充电上限压在 80%。而模块**没有插拔检测**
（v11.6 时被当作"和 WebUI 重复"删掉了），于是：

- 拔掉充电器后模块仍认为自己在旁路，`night_charging` 一直挂着；
- 重新插上时，框架先把电充到 80% 就停 —— **用户设的阈值（比如 90）在这条路径上失效**。

**改法（两半，缺一不可）**：

1. **拔掉 → 立刻退出旁路**。主循环的等待从 `nap` 换成 `nap_watch`：
   把一轮 60 秒拆成 5 秒一步，每步瞄一眼 `usb/online`，一旦读到 `0` 就提前返回主循环，
   由主循环执行退出序列（写 `night_charging=0` + `current_cmd="0 0"`）。
   代价：旁路态下每分钟多约 11 次 fork（`sleep` 是 busybox 的 NOFORK applet，1ms 级）。
2. **没有充电器时【不进入】旁路**。进入条件加 `usb/online != 0`（读不到就按老行为放行）。
   不加这一条的话，刚退出又会立刻进入，等于白做 —— 而且又会把 `night_charging` 挂上。

最终状态机：

```
充电器在线 且 电量 >= ENABLE_THRESHOLD   -> 进入旁路
充电器在线 且 电量 <= DISABLE_THRESHOLD  -> 退出旁路
充电器被拔掉                             -> 立刻退出旁路（≤5 秒）
没有充电器时                             -> 不会进入旁路
```

**已验证的那一半**：23:36 充电器是拔掉状态，daemon 停在 `state=off`、
`current_cmd=[0 0]`、`night_charging=0(644)`，**没有进入旁路**（tick 日志：`usb_on=0`）。

**还没验的那一半**：插着旁路时**物理拔掉** → 5 秒内自动退出。需要一次真实动作。

### 16.3 `tick` 日志新增 `usb_on=`

```
tick cap=87 state=on ibat=0 usb_on=1 usb_in=687 node=[0 1] cp=1 type=USB_PD
```

插拔排查全靠它 —— 之前只有 `usb_in`，而 `usb_in=0` 有两种含义（PD 走泵 / 适配器已拔），
分不清。README §4.3 的日志格式说明已同步。

### 17.4 ★ `uninstall.sh` 的顺序 bug（会真的坏）

```sh
ulog() { echo "$(date '+%Y-%m-%d %H:%M:%S') uninstall: $*" >> "$STATE_DIR/run.log"; }
...
elif printf '%s\n' "$val" > "$node" 2>/dev/null; then
  ulog "还原 $node = $val  (读回=$(cat "$node" 2>/dev/null))"
else
  ulog "FAILED 还原 $node = $val"
```

**副产品**：以后"卸载是否干净"只要 `grep uninstall: run.log` 就有实证 ——

## 十八、v12.1：运行模式（自动 / 手动旁路）+ WebUI 手动操作（2026-10-06 23:44–23:48）

### 18.1 需求与设计

用户要求：**WebUI 加回"手动操作"，分成「自动」和「开启旁路」两项，并显示模式状态。**

关键点：**不能只做两个按钮**。如果"开启旁路"只是一次性写入节点，
守护进程下一轮就会按阈值把它改回去（比如在 65% 时手动开旁路，下一轮 `cap ≤ DISABLE` 又会退出）。
所以必须让守护进程**认一个模式**：

| 模式 | 谁决定进/出旁路 | 进入条件 | 退出条件 |
|---|---|---|---|
| `auto`（默认） | 按配置阈值 | `usb/online≠0` 且 `capacity ≥ ENABLE_THRESHOLD` | `capacity ≤ DISABLE_THRESHOLD` |
| `on`（手动旁路） | 用户，**无视阈值** | `usb/online≠0`（插着就保持） | **只有**：拔充电器 / 切回 `auto` / 卸载或重启 |

两种模式**都保留**：拔充电器退出（§16.2）、自愈重打（§15.8）、"没充电器不进旁路"、
写入前解锁 / 写入后上锁（§16.1）。手动模式**不是**"无人看管的旁路"。

### 18.2 实现

1. **模式存哪**：`$STATE_DIR/mode`，内容就是 `auto` 或 `on` 两个词。
   为什么单独一个文件而不是塞进 `config.sh`：守护进程每轮都要读它，
   而 `config.sh` 只在启动时解析一次；单独文件一次 `read` 内建（不 fork）就够了。
   **文件不存在或内容不认识 → 一律按 `auto`**（删掉它等于恢复自动）。
2. **守护进程**：主循环里 `read_mode`；模式变化时记一条 `模式切换：X -> Y`；
   进入/退出判定按模式分叉（`on` 只判 `usb/online`，不判阈值）。
3. **`bypassctl.sh`**：新增 `mode auto|on` 子命令；`status` 增加 `MODE=` 字段。
4. **即时生效（USR1）**：切完模式给守护进程发 `USR1`，让它不用等满一轮。
   这里踩了一个坑（见 18.3），最后用 `WAKE` 标志解决。

### 18.3 ★ 踩的坑：`USR1` 只打断 `wait`，打不断"分格睡"

第一版实现是：`trap 'kill $SLEEP_PID' USR1`，想着"信号会打断 `wait`，循环就继续了"。

**实测：没有立刻生效。** 原因是主循环的等待用的是 `nap_watch` ——
它是"5 秒一格、共 12 格"的循环。信号只打断了当前那一格的 `wait`，
`nap_watch` 接着睡下一格，等于只少睡了几秒。

**修法**：信号处理里额外置 `WAKE=1`，`nap_watch` 在每格开头和 `wait` 返回后都检查它，
一旦为 1 就 `return`；主循环每轮开头把 `WAKE` 清零。

**验证**（真机日志，同一秒）：

```
23:47:31 执行 bypassctl.sh mode on
23:47:31 模式切换：auto -> on        ← 同一秒
23:47:36 执行 bypassctl.sh mode auto
23:47:36 模式切换：on -> auto        ← 同一秒
```

### 18.4 WebUI

- 新增「**手动操作**」卡片：**自动** / **开启旁路** 两个按钮（`#btn-auto` / `#btn-on`），
  当前模式对应的那个按钮高亮（`.active`）。
- 状态卡片新增「**模式**」行：胶囊显示 `自动`（蓝）或 `手动旁路`（绿）+ 一行小字说明
  （`无视阈值，插着就保持旁路`）。
- 徽章在手动模式下写成「**旁路已开启（手动）**」，和自动模式区分开。
- 按钮走 `ksu.exec(CTL + ' mode auto|on')`，然后延迟 700ms 刷新一次状态。

> 注意与 v11.12 的关系：那次删掉的「手动操作」是 4 个**一次性动作**按钮
> （立即进入 / 立即恢复 / 刷新 / 重启），这次加回的是 2 个**模式**按钮，语义不同。
> README §5 里已把"删过什么/加回什么"列成一张表，免得以后又来回折腾。

### 18.6 ★ 又一个"观察窗口太短"的实例：真旁路要 ~10 秒才收敛

第一次测手动旁路时，我在写入后只采了 3 条（间隔 3 秒）就看到 `ibat=+190mA`，
当场判断"进了旁路但只是停充、不是真旁路"。**重新拉长窗口后才发现那只是过渡期**：

```
23:52:42 刚写入    ibat=-43000   usb_in=20   en_pp=1
23:52:45 过渡      ibat=+428000  usb_in=20   en_pp=1   ← 适配器还没接管，电池临时供电
23:52:49 过渡      ibat=+130000  usb_in=20   en_pp=1
23:52:52 收敛      ibat=0        usb_in=210  en_pp=1   ← ★ 真旁路
23:52:55 收敛      ibat=0        usb_in=175  cp=3
23:52:58 收敛      ibat=0        usb_in=292  cp=3
```

自动模式也一样（恢复 80/70 后：`ibat=+126000` → 4 秒后 `ibat=0, usb_in=185`）。

**结论**：`en_power_path=1` 写进去之后，主电源路径要**约 10 秒**才真正把系统负载接过去；
这期间电池会短暂供电（`ibat` 为正）。**判断"是不是真旁路"至少要看 15~20 秒**，
只看前 3~6 秒会误判成"停充"。

> §14.3 的 `input_current`）。三次的教训写在一起：**先等够时间，再下结论。**

## 十九、v12.2：自愈扩到三条 + 进入后 10 秒复核（2026-10-06 23:58–00:07）

### 19.1 起因：自愈有个盲区

原来的自愈只抓一种失效：**「说在旁路、但电池还在充」**（`ibat < -150mA`）。

> 泵确实被压下去了，可 `en_power_path` 没使能 → **只做到"停充"**：
> 系统靠电池跑、`ibat` 明显为正、电量慢慢掉。用户看到的是"模式说在旁路、电量却在掉"。

这种失败原来是**完全静默**的（`ibat` 为正，不满足"还在充"的判据，自愈不会触发）。

### 19.2 新增第 ③ 条判据（关键是"三条一起看"）

```
① 电池仍在充      ibat < -150mA 且 usb/online=1
② 锁定节点掉了    night_charging ≠ 1
③ 只做到停充      ibat > +30mA 且 usb/online=1 且 en_power_path ≠ 1     ← v12.2 新增
```

**为什么第 ③ 条必须带上 `en_power_path`**：供电不足的适配器（电脑 USB 口）下，
即使旁路完全正常、电池也会放电补差额（`bypassctl.sh` 的老注释就提醒过这点）。
那种情况 `en_power_path` 是 `1`，加上这个条件就不会误判。
读到的值放在 `PP_LAST` 里，日志会带上，方便事后判断。

选 10 秒的依据就是 §18.6 测出来的收敛时间（主电源路径接管系统负载约需 10 秒）。

## 二十一、v12.3：日志只保留最近 30 条（2026-10-07 00:18）

### 21.1 改动

用户要求：**日志文件只保留最近三十条**。

`log()` 原来是这样控制体积的：每 32 条查一次文件大小，超 64KB 就整体改名成 `run.log.old`
（也就是"轮转 + 丢历史"）。现在改成**截尾**：

```sh
LOG_KEEP_LINES=30
log() {
  echo "$(date '+%Y-%m-%d %H:%M:%S') $*" >> "$LOG_FILE"
  LOG_LINES=$((LOG_LINES + 1))
  if [ "$LOG_LINES" -gt "$LOG_KEEP_LINES" ]; then
    tail -n "$LOG_KEEP_LINES" "$LOG_FILE" > "$LOG_FILE.tmp" && mv -f "$LOG_FILE.tmp" "$LOG_FILE"
    LOG_LINES=$LOG_KEEP_LINES
    LOG_PERM_SET=0        # mv 之后是新文件，权限要重设
  fi
  [ "$LOG_PERM_SET" = "0" ] && chmod 600 "$LOG_FILE" && LOG_PERM_SET=1
}
```

- `LOG_LINES` 在守护进程启动时用一次 `wc -l` 初始化（只有一个 fork）。
- 为什么这样适合正式版：DEBUG=0 之后一天也就几条决策记录（模式切换/进旁路/自愈/拔插/报错），
  30 条足够看"最近发生了什么"，而文件永远很小、WebUI 里不用滚动。
- 代价：写满之后每条多一次 `tail` + `mv`（两个 fork，约 20~40ms）。可忽略。
- `run.log.old` 不再生成（旧的那个文件留着没删，里面是很久以前的历史，确认不需要可以删）。

### 21.2 部署与验证

```
部署前 run.log：561 行
tail -n 30 截尾后：30 行
重启守护进程（新代码接管）：30 行，并保持
```

**顺带印证了 v12.2 的新日志格式**（这条正好是充电器被拔掉时记的）：

```
2026-10-07 00:18:00 start pid=4127 on>=80 off<=70 interval=60s debug=0
2026-10-07 00:18:00 mode=auto  (auto=按阈值自动 / on=手动强制旁路，无视阈值)
2026-10-07 00:18:00 initial state=on
2026-10-07 00:18:03 bypass OFF (capacity=87 / 充电器已拔)      ← 新格式（v12.2 抽函数后带上原因后缀）
```

### 21.3 ⚠️ 这个策略的取舍（写下来免得以后困惑）

30 条是**很短**的窗口：
- DEBUG=0 时约能覆盖**最近一两天**的决策；
- 一旦把 `DEBUG=1` 打开，每轮一条 `tick`，**30 条只够 30 分钟**，什么历史都留不下；
- 所以"要留证据"的正确做法是**当时就把日志导出**（`grep`/`cp` 出来），
  而不是指望 run.log 帮你记住。

（`LOG_KEEP_LINES` 是脚本顶部的常量，想改成 100 或 1000 改一行即可。）

## 二十二、★ 事故复盘：发行版 zip 的条目名用了反斜杠，把 WebUI 装没了（2026-10-07）

### 22.1 现象

用户报告："我让你删注释，你怎么把 webui 也删了？" —— 手机上模块**没有 WebUI**。

### 22.2 定位顺序（值得记住）

1. **先验证"我刚改的东西"**：把带注释的源码与发行版的 `webroot/index.html` 逐行对比 ——
   差异 39 行，**其中 0 行不是注释或空行**，HTML/CSS/JS **一行代码都没动**；
   20 个 JS 引用的元素 ID 全部存在；`node --check` 通过；没有老 WebView 不支持的语法。
   → **代码没问题**，方向立刻转向"安装产物"。
2. **再查手机上的文件**：`ls -l $M/webroot/index.html` → `No such file or directory`。
   `ls -la $M` 一句话解释了一切：

   ```
   -rw-r--r-- 1 root root 14549  webroot\index.html                       ← 平铺文件！名字里带反斜杠
   -rw-r--r-- 1 root root   612  META-INF\com\google\android\update-binary
   ```

   `[ -d $M/webroot ]` → **根本没有 webroot 目录** → KernelSU 找不到 `webroot/index.html`
   → 管理器的 WebUI 入口拿不到内容。
3. **查 md5 锁定来源**：手机上那 6 个脚本的 md5 与**发行版**逐一完全一致 → 用户装的是发行版 zip，
   所以问题出在发行版 zip 的打包环节。

### 22.3 根因：zip 条目名的分隔符

打包脚本 里打包原来是调 `powershell.exe`（**Windows PowerShell 5.1 / .NET Framework**）
的 `ZipFile::CreateFromDirectory`。它的条目名用**反斜杠**：

```
PS 5.1 生成：  [a\x.txt]  [a\b\y.txt]        ← 反斜杠
bsdtar 生成：  [a/x.txt]  [a/b/y.txt]        ← 正斜杠
```

zip 规范要求正斜杠，而**安卓的解压实现不会把反斜杠当路径分隔符** ——
于是 `webroot/index.html` 变成"一个名字里带反斜杠的平铺文件"，`webroot/` 目录不存在；
`META-INF/...` 同样变成模块根目录下的两个平铺文件。

> **为什么以前一直没事**：之前的 zip 都是我直接用 **pwsh 7**（.NET Core，正斜杠）打的，
> 只有走生成器脚本的**发行版 zip** 才踩到 5.1 这个坑 —— 也就是"我新加的工具引入了新 bug"。

### 22.4 修复

1. **生成器改用 bsdtar**（Windows 自带 `C:\Windows\System32\tar.exe`）：
   `tar -a -c -f out.zip -C <源码目录> <每个文件的相对路径>`，条目名即相对路径（正斜杠）。
2. **打完自动自查**：条目名里不许有反斜杠，且必须存在 `webroot/index.html`，否则报错并以退出码 1 结束。
   实现上**用纯 JS 读 zip 的中央目录**（EOCD → 中央目录逐条读文件名），
   **不调外部命令**。
3. **真机修复**：用修好的 zip 走 `ksud module install` 正规安装。
   KernelSU 把文件解到 `/data/adb/modules_update/bypass_charger/` 并给模块目录打一个 `update` 标记
   （重启后应用）；安装日志里明确写着 `inflating: webroot/index.html`（正斜杠 ✔）。
   实测待更新目录里的 `webroot/index.html` = **15639 字节 / md5 `cfd072b5...`**，与交付源码一致。

### 22.5 教训

> **① 打包 Android 模块时，zip 条目名必须逐个检查分隔符。**
> 反斜杠在 Windows 上"看起来完全正常"（资源管理器、`Expand-Archive` 都能解），
> 只有到了安卓才暴露成一个诡异命名的平铺文件，而且**全程不报错** ——
> 表现就是"功能凭空消失"。所以生成器里加了硬性自查。
>
> **② 先验证"我改的东西"，再验证"对方看到的现象"。**
> 22.2 的第 1 步（逐行对比）只花了一分钟就排除了代码问题，把方向直接指到安装产物；
> 否则很容易在 WebUI 代码里瞎找半天。
>
> **③ "看起来能用"不等于"装到目标平台上能用"。**
> 这个 zip 在本机解压一切正常，验证也全过 —— 因为我的验证用的是同一套 .NET 解压。
> **验证要用目标平台的解压器**（这次是安卓/KernelSU 的 unzip）。
